## 一、结论先行

**整体可行。** 这是一个数据量小、交互简单、无重计算的本地工具类应用，技术上门槛很低。真正的风险不在"能不能做"，而在三处：

1. **重复任务的数据模型**（功能一 / 二的地基）—— 语义没定清就会返工。见 §2.1。
2. **安卓端的提醒与后台存活**（功能一"提示"）—— 国产 ROM 是硬坑，不是代码问题，是系统限制。
3. **安卓桌面卡片**（功能四延伸）—— 绝大多数跨平台框架不直接支持，必须落一段平台原生代码。这一条会**反向决定技术栈**。

**⚠️ 技术栈结论已修订两次。**

- §5~§8：未告知团队背景时的通用对比，**作废**。
- §9~§11：基于 Java + Vue 的推演，**部分作废**（约束已放开）。
- **§12：最终方案，以这节为准。**

最终结论：**前端 = Tauri 2 + Vue 3（PC 与 Android 共用一套前端代码）+ Android 原生 Kotlin 插件承载整月网格卡片与闹钟；后端 = Go 单文件自托管服务，只负责同步与合并，前端不强依赖它。**

## 二、需求拆解与必须敲定的语义

需求初稿里有几处表述在实现时会分叉成完全不同的数据模型。**这几个点建议在写第一行代码前定死。**

### 2.1 功能一：周期任务 —— 核心歧义

> "创建一个或多个任务，选择重复，根据选择的日期时间段是几天来重复，类似于工作量，或者排版那种，可以打卡任务是否完成，完成这个周期的时间段就只会提示这个任务完成"

这段话至少有三种可能的读法，模型不一样：

| 读法 | 含义 | 数据模型 | 首页表现 |
|---|---|---|---|
| A. 逐日摊派 | 任务从 D1 到 D2 共 N 天，**每天各需打卡一次** | 任务 × N 个日期实例 | 每一天格子里都出现该任务 |
| B. 整段一次 | D1~D2 是**一个周期**，周期内完成一次就算完成 | 1 个任务 + 1 个区间状态 | 只在 D2（或当前日）出现"待完成/已完成" |
| C. 累计工作量 | 周期内需完成 K 次（"工作量"），不限定哪天 | 任务 + 计数 progress/target | 显示 3/5 进度 |

初稿里"类似于工作量"倾向 C，"完成这个周期的时间段就只会提示这个任务完成"倾向 B。**建议 MVP 先实现 A + B 两种（覆盖 80% 日历类应用的使用场景），C 作为二期。**
如果确实要 A、B、C 全支持，模型上留一个策略字段即可，不用三套表：

```
Task
  id, title, note
  startDate, endDate          # LocalDate，不是时间戳
  scheduleType                # ONCE | DAILY | WEEKLY | MONTHLY | YEARLY | CUSTOM
  interval                    # 每 N 个单位，如每 2 周
  byWeekday                   # CUSTOM 用：周一/三/五
  dayStartTime                # 可选，有具体时刻才有提醒
  completionMode              # PER_DAY(A) | WHOLE_RANGE(B) | COUNT(C)
  targetCount                 # C 模式用
  remindOffsetMinutes         # -1 表示不提醒
```

**关于"重复规则"的重要建议：不要引标准 RRULE。** iCalendar RRULE 的完整语义（BYSETPOS、跨夏令时、月末 31 号、闰年 2/29）实现和调试成本远超本项目收益。自己写一个受限规则集（上面那几个字段）足够，且行为可控、用户能理解。

### 2.2 功能二：时间单位"年月周日时"

> "创建任务可以选择时间是否做了（可以细分选择时间单位：年月周日时）"

这里的"年月周日时"有两种解释：

- **单次任务的时刻精度**：只选一个时点/一天/一周 —— 那是创建表单的粒度选择。
- **重复周期的单位**：每 X 时 / 每 X 日 / 每 X 周 / 每 X 月 / 每 X 年 —— 那属于 §2.1 的 interval + 单位。

按字面"是否重复"的上下文，更像第二种。**注意"时"这个粒度：** 一旦支持小时级重复，就必须依赖精确闹钟（§4.4），安卓 12+ 要额外权限，且 Google Play 上架需要说明理由。若可接受，建议把"时"限制为**当天内的时刻提醒**，跨天的周期最小单位到"日"。这是绝大多数同类应用的取舍（滴答清单、Todoist 都是这个边界）。

另："默认点击任务会选择是否完成" —— 即**单击 = 切换完成态**，不加确认弹窗，但要给 3~5 秒撤销（Undo Snackbar）。误触是打卡类应用最高频的投诉点。

### 2.3 功能三：记事本

> "标题+内容（限制时间）…… 在首页的对应日期展示这个标题"

- "限制时间"歧义：(a) 内容长度上限；(b) 这条记事挂在哪一天/哪段时间。按"首页对应日期展示"看，是 (b)。
- 实现上它跟"全天任务"几乎同构，**建议共用一张表，用 `kind` 区分**（TASK / NOTE / COUNTDOWN），只是首页渲染成不同样式（记事显示为小标签/斜体标题，不参与打卡统计）。做成三张独立表是早期最容易犯的过度设计。
- 注意正文长度：如果是长文本，别塞进列表查询里。列表查只取标题 + 摘要，正文按需加载。

### 2.4 功能四：倒数日 + 安卓桌面

- **倒数日本体：零技术难度**，纯日期差计算。唯一要处理的边界是"每年重复"遇上 **2 月 29 日**（非闰年取 2/28 还是 3/1，得定一个）和跨时区。
- **安卓桌面卡片：可行，但有几个必须知道的限制**，见 §4.5。
- **锁屏卡片：不建议写进需求。** AOSP 没有通用的第三方锁屏小组件 API，只有三星/小米等厂商 ROM 的私有扩展。做出来只能覆盖少数机型，维护成本很高。

### 2.5 整体形态

月历网格 + 格子内小标签 + 右上角齿轮（全局默认周期 / 提醒 / 周起始日）。这部分没有任何技术风险。两个细节：

- **格子空间极窄**：一个日期格里塞 3 条以上就放不下。要有 "+N" 折叠和点击展开的日视图。
- **周起始日**（周一/周日）必须做成设置项，否则国内用户会吵。

## 三、可行性评级

| 需求 | 可行性 | 难度 | 主要风险 |
|---|---|---|---|
| 功能一 周期任务 + 打卡 | 可行 | 中 | 重复规则语义、A/B/C 模式取舍 |
| 功能二 创建时选时间单位 | 可行 | 低-中 | 小时级 → 精确闹钟权限 |
| 功能三 记事（标题+内容） | 可行 | 低 | 与任务表的复用边界 |
| 功能四 倒数日 | 可行 | 低 | 闰年 2/29、时区 |
| 安卓桌面卡片 | 可行 | 中-高 | 框架支持度、更新频率限制、需原生代码 |
| 安卓锁屏卡片 | 不推荐 | 高 | 无通用 API，仅厂商 ROM |
| 提醒/定时（"提示"） | 可行 | 中-高 | 国产 ROM 后台查杀、厂商白名单 |
| 月历首页 + 设置页 | 可行 | 低 | 格子密度、周起始日 |
| 双端数据同步（若需要） | 可行 | 高 | 冲突合并、账号体系，工作量翻倍 |

**总体判断：作为单人/小团队产品，核心 MVP 4~6 周可到可用状态（单端 Android + 桌面卡片）；加 PC 端同步再 +3~4 周；加云同步至少 +4~6 周。**

## 四、技术难点与关键补充（不写代码，但会决定架构）

### 4.1 重复任务：虚拟展开 vs 预生成实例

打卡状态必须落库，但"每天重复到无限远"不可能全写进数据库。三种做法：

| 做法 | 优点 | 缺点 |
|---|---|---|
| 查询时纯计算展开 | 零存储 | 打卡记录要单独按 (taskId, date) 存，统计/提醒要重复展开 |
| 全部预生成 | 逻辑最简单 | 无限重复无法预生成；改规则要批量改历史 |
| **混合（推荐）** | 折中 | 稍复杂 |

推荐做法：**模板只存规则；打卡记录表 `Completion(taskId, date, status, completedAt)` 独立存；查询某月时按规则展开该月 + 左连接 completion 表。**
预生成只用于"未来 90 天内的提醒实例"（因为要给 AlarmManager 注册闹钟，必须提前落到具体时刻）。这样既不会写出百万行垃圾数据，提醒也不会漏。

改规则时的语义要定：**改规则只影响未来，历史打卡不动**。这条要写进需求，否则用户改一次重复规则就把上月打卡记录全洗掉，是数据事故。

### 4.2 日期就用 LocalDate，不要用时间戳

任务/记事/打卡全部是"日历日"语义，不是时间点。用 `LocalDate`（Kotlin `java.time.LocalDate`、Dart `DateTime` 但只取年月日、TS 里用字符串 `YYYY-MM-DD`）存，**不要存 epoch 毫秒**。否则跨时区、旅行、夏令时会整片日期漂移一格。这类 bug 极其难查。
需要精确提醒的才额外存一个"当日时刻"。

### 4.3 数据库

- 单端本地：SQLite。
  - Kotlin/CMP：**SQLDelight**（编译期校验 SQL，跨平台）
  - Flutter：**Drift**（类型安全）或 sqflite
  - RN：Drizzle / WatermelonDB / expo-sqlite
  - Tauri：tauri-plugin-sql 或 Rust 侧 rusqlite
- 同步云端（若做）：Postgres（Supabase 自带 Auth/Realtime），或自建 + 增量同步。
- **不推荐用纯文档型 NoSQL 存这种强日期查询的数据**，月视图查询会很别扭。

### 4.4 提醒与后台存活 —— 安卓端最大坑

这一项初稿没展开，但它决定"提示"功能能不能真的按时响。

1. **权限三连**：
   - Android 13+ `POST_NOTIFICATIONS`（运行时请求）
   - Android 12+ 精确闹钟：`SCHEDULE_EXACT_ALARM`（可被用户关）或 `USE_EXACT_ALARM`（系统级，**Google Play 上架要审核理由**，只有闹钟/日历类应用可申请）
   - Android 12+ 开机自启/后台：`RECEIVE_BOOT_COMPLETED` + 重新注册闹钟（重启后闹钟全丢，必须自己重建）
2. **定时机制**：`AlarmManager.setExactAndAllowWhileIdle` 是唯一能穿透 Doze 的模式，但系统对它有配额（约每分钟一次），且非精确模式下系统可推迟。WorkManager 最小周期 15 分钟，只能做"补漏扫描"，不能当主闹钟。
3. **国产 ROM（MIUI / ColorOS / EMUI / HyperOS）**：这些是真正的坑。后台进程被杀、自启被拦、通知被静音，**代码层面无解**。标准做法：
   - 应用内做"保活引导页"，检测厂商并提供跳转各 ROM 自启动/电池白名单设置的入口
   - 用前台服务兜底（会常驻一条通知，用户体验下降，需权衡）
   - 提醒逻辑设计成"打开应用时补算"，而不是纯粹依赖推送（漏了就补上，至少数据不丢）
4. **PC 端提醒**：比安卓简单。Windows 托盘常驻 + Toast（`ToastNotificationManager` / 第三方库），或直接用系统任务计划；macOS 用 `UNUserNotificationCenter`。**PC 端要做"最小化到托盘 + 开机自启"开关**，否则"提示"就是摆设。

### 4.5 安卓桌面卡片（App Widget）—— 技术真相

先说结论：**能做，而且这是本项目最有差异化的点；但没有任何一个跨平台 UI 框架能"顺带"把它做出来，必须写一段 Android 原生。**

- **实现方式**：Android 12+ 用 **Jetpack Glance**（Compose 风格 API，推荐）；低于 12 用传统 `RemoteViews + AppWidgetProvider`。两者都要写。
- **交互限制**：卡片里的点击**只能触发 PendingIntent**，不能直接跑应用内逻辑。所以"在卡片上直接勾选完成"要实现成：PendingIntent → 透明 Activity 或 BroadcastReceiver → 写本地库 → 通知卡片刷新。
- **刷新频率限制**：`updatePeriodMillis` 最小 **30 分钟**，且系统会合并。要做到"打开就最新"，必须**应用内数据变更时主动推送刷新**（`AppWidgetManager.notifyAppWidgetViewDataChanged` / Glance 的 `updateAll`），加上跨天自动刷新要注册一个零点附近的闹钟。
- **跨平台框架的支持现状**（这是选型的分水岭）：
  - **Compose Multiplatform / 纯 Kotlin**：同一个 Gradle 工程里直接写 Glance，**零摩擦**。这是它的核心优势。
  - **Flutter**：`home_widget` 插件只做数据桥接（SharedPreferences），**卡片的 UI 和交互仍要写 Kotlin**，等于维护两套。能做，但有额外成本。
  - **React Native**：需要自己写原生模块 + headless JS，链路更长；`expo` 托管模式下基本做不了。
  - **Tauri 2 / Capacitor**：移动端生态本身尚不成熟，卡片要靠原生插件包一层。
- **卡片预览**：Android 12+ 支持 `previewLayout` / `descriptionRes`，在"选择小组件"面板里显示示意图，实现简单，值得做。
- **锁屏卡片**：见 §2.4，不建议做。

### 4.6 数据备份 / 多端同步（初稿未提，但迟早要面对）

问题：**"pc + app"是否要求数据互通？** 这是最大的工作量分水岭。

- 只要"两端各用各的"：两端共用同一份 schema，本地 SQLite，**工作量小一个数量级**。
- 要互通：必须做账号体系 + 云端中转 + 冲突合并（同一任务两端同时打卡怎么办？规则用 last-write-wins 还是按字段合并？）+ 离线队列。**这部分工作量通常超过主功能本身。**

建议：**MVP 阶段用"导出/导入 JSON + 局域网/网盘文件同步"过渡**，把云同步明确放到二期。功能上不丢人，工程上省一个月。

### 4.7 PC 端的形态选择

三种，影响不小：

- **纯桌面窗口应用**：最简单，但用户关了就不提醒。
- **托盘常驻 + 开机自启**（推荐）：符合"日程提醒"类工具的使用习惯。
- **纯 Web**：开发最省，但拿不到系统通知、开机自启、本地文件，且安卓卡片完全没戏。

Kotlin/CMP 的桌面端跑在 JVM 上：**启动约 1~2 秒、内存 150~300MB**，比 Electron 轻、比原生重。若能接受 JVM，可打包成自带运行时的安装包（30~60MB）；对体积敏感可以用 GraalVM native-image 编译成原生可执行文件（体积降到 15~25MB，启动变快，但反射/序列化要额外配置，是个坑）。

## 五、技术栈方案对比

前提：**一套代码覆盖 PC + Android**，且需要安卓桌面卡片。

### 方案 A · Kotlin Multiplatform + Compose Multiplatform（推荐）

| 项 | 内容 |
|---|---|
| 语言 | Kotlin（业务 + UI 全用）；卡片/通知直接用 Android 原生 Kotlin |
| PC | Compose for Desktop（JVM），可打包 msi/dmg；或 GraalVM native-image |
| Android | 原生 Kotlin，零桥接 |
| 桌面卡片 | Jetpack Glance，**同一工程直接写** |
| 数据库 | SQLDelight |
| 优点 | 卡片/闹钟/权限/通知全部原生直用，无跨语言桥接；桌面与移动 UI 共享；安卓体验天花板最高 |
| 缺点 | 桌面端 JVM 启动慢、内存偏高、打包体积中等；桌面生态（表格、富文本、系统集成）比 Flutter/Electron 弱；团队若非 Kotlin 背景要学 |
| 适合 | **安卓体验优先、卡片是核心卖点、愿意只做 Windows+Android** |

### 方案 B · Flutter

| 项 | 内容 |
|---|---|
| 语言 | Dart（+ 安卓侧 Kotlin 写卡片和部分通知） |
| PC | Flutter Windows/macOS/Linux（成熟度中等） |
| Android | Flutter Android |
| 桌面卡片 | `home_widget` 只做数据桥，**UI 需 Kotlin 另写一套** |
| 数据库 | Drift / sqflite |
| 优点 | 生态最大、组件最全、渲染一致性最好、日历/图表类开源包多、招人容易；一套 UI 两端一致 |
| 缺点 | 桌面端文本渲染、输入法、无障碍偏弱；包体积较大；**卡片要维护两套代码** |
| 适合 | 通用型产品、团队已会 Dart/Flutter、卡片只做基础展示 |

### 方案 C · React Native (+ Expo)

| 项 | 内容 |
|---|---|
| 语言 | TypeScript（+ Kotlin/Objective-C 原生模块） |
| PC | 无官方路径，需 Electron / Tauri / react-native-windows 另起一套 |
| 桌面卡片 | 需自写原生模块，Expo 托管模式做不到 |
| 优点 | Web 团队上手最快、生态庞大 |
| 缺点 | **PC 端是最大短板**：要么另起 Electron 工程（等于两套），要么用不成熟的 RN-Windows；卡片链路长 |
| 适合 | 不推荐用于"PC 优先 + 安卓卡片"这种组合 |

### 方案 D · Tauri 2（Rust + Web 前端）

| 项 | 内容 |
|---|---|
| 语言 | TypeScript（UI）+ Rust（后端/系统调用） |
| PC | **优秀**：安装包约 5~10MB，内存低，系统集成好，托盘/自启/通知都有成熟插件 |
| Android | Tauri 2 已正式支持 Android/iOS，但移动端生态仍偏早期，插件覆盖率低 |
| 桌面卡片 | 无现成方案，需写原生 Kotlin 插件包一层 |
| 数据库 | tauri-plugin-sql + SQLite |
| 优点 | PC 端最强（轻、快、省内存）；Web 前端开发效率高 |
| 缺点 | Android 侧要你既懂 Rust 又懂 Kotlin；生态插件少，遇到坑自己填；两语言栈 |
| 适合 | **PC 是主战场、安卓只是附带**的产品 |

### 方案 E · Capacitor / Cordova（Web 壳）

| 项 | 内容 |
|---|---|
| 语言 | TypeScript + 原生 Kotlin（插件） |
| PC | 走 PWA，或再套 Electron（体积大） |
| Android | Capacitor 打包 WebView |
| 优点 | Web 团队零门槛迁移 |
| 缺点 | **WebView 渲染日历网格 + 大量列表滚动时性能明显不如原生**；卡片/闹钟仍需原生插件；PC 端没有好答案 |

# 九、技术栈修订（已知团队为 Java + Vue）

## 9.1 功能一语义确认后的数据模型

你的描述已经收敛成两种任务形态 + 一个重复开关，模型比我原先设想的三选一简单得多：

```
Task
  id            TEXT     -- UUID
  title         TEXT
  note          TEXT
  kind          TEXT     -- TASK | NOTE | COUNTDOWN（记事、倒数日共用表，靠这个区分）

  -- 形态①：连续日期区间，如 3/1 ~ 3/3
  startDate     TEXT     -- 'YYYY-MM-DD'，LocalDate 语义，不存时间戳
  endDate       TEXT     -- 同上，单日任务时 == startDate

  -- 形态②：每周固定几天，如 周一 ~ 周三
  weekdaysMask  INTEGER  -- 位掩码，bit0=周一 ... bit6=周日；0 表示不用此形态

  repeat        INTEGER  -- 0=不重复（只出现一次） 1=重复
  repeatUntil   TEXT     -- 可空，重复的终止日；空=永久重复
  repeatEveryDays INTEGER -- 可选：形态①的重复间隔，如"每 7 天重复这 3 天"
  lastSyncedRev ...
```

**规则展开的语义（按你的描述固化）：**

- `weekdaysMask` 有值 + `repeat=1` → **每周**的这几天都出现。选周一~周三，就是之后每一周的周一、周二、周三各出现一次。
- `startDate~endDate` + `repeat=0` → 只在这一次区间内出现。
- `startDate~endDate` + `repeat=1` + `repeatEveryDays=N` → 从这个区间开始，每隔 N 天再出现同样长度的区间。

**还剩一个必须敲死的点**（这个影响打卡表结构，成本很低但要先定）：

> 「周一~周三」出现后，是**三天各自独立打卡**（周一打完不影响周二），还是**整段算一次、打一次卡整段完成**？

我按你原话"完成这个周期的时间段就只会提示这个任务完成"理解为**后者**（整段一次），但又提到"打卡任务是否完成"像是逐日。
**建议：做成创建时的一个选项 `completionMode`，默认"逐日独立打卡"**（更符合日历类应用习惯，且更自由），另一档"整段一次"作为可选项。一个字段的差别，别留到后期改。

**打卡记录单独一张表**，不要塞进任务表：

```
Completion
  id        TEXT
  taskId    TEXT
  occurDate TEXT      -- 'YYYY-MM-DD'
  status    INTEGER   -- 0未完成 1已完成
  updatedAt INTEGER   -- 合并用
  deviceId  TEXT      -- 合并用
  deleted   INTEGER   -- 软删，同步必须
```

月视图查询 = 按规则展开当月 → 左连接 Completion。**规则本身不预生成实体行**，否则"永久重复"的规则会写出无限数据；只有未来 90 天内需要提醒的实例才落"提醒排程表"。

**红线：改规则只影响未来，历史打卡记录不动。** 用户改一次重复规则就洗掉上月记录，是这类应用最典型的翻车方式。

# 十、局域网同步方案设计（⚠️ 已被 §12 取代）

> **本节作废。** 在确认"同步拆成独立后端服务、前端可独立运行"之后，点对点端口发现（UDP 广播 / 网段扫描 / 两端对称实现 / 双份合并逻辑）整块不再需要，且合并逻辑从"写两遍"变成"只写一遍"。
> **请直接看 §12。** 本节保留仅作对照：万一后续要回到 P2P 模式，坑的清单在这里。

你的设想是"扫描固定端口 → 发现 → 验证 → 上传合并"。方向对，但直接照做会踩四个坑。下面按层给方案。

## 10.1 发现层：纯端口扫描会踩的坑

**坑 1 · 扫哪个网段？**
必须先拿到"本机的 IP + 子网掩码/前缀长度"再推算出网段，否则 192.168 和 10.x 和 172.16-31 三种私有网段全扫一遍，254×3 = 762 个地址，纯 TCP 超时探测要几十秒。
- Android：`ConnectivityManager` + `LinkProperties.linkAddresses` 拿前缀长度（新版 `WifiManager.getConnectionInfo()` 受限）
- Electron/Node：`os.networkInterfaces()` 遍历非 internal 的 IPv4，拿 `netmask` 算 CIDR

**坑 2 · 并发与超时**
`nc -z` 式的串行扫描不可接受。正确做法：TCP `connect` 超时设 **150~250ms**，并发度 64~100，整个 /24 网段约 **1~2 秒**出结果。Node 用 `Promise.allSettled` 分批；Java 用 `ExecutorService` + `Future`。
单纯端口扫描还有个副作用：**会被 Windows Defender / 企业安全软件 / 部分路由器当成端口扫描行为**，可能弹告警甚至封 IP。

**坑 3 · 广播更省事，但可能被拦**
推荐**双策略**，而不是只做扫描：

1. **优先 UDP 广播**：向子网定向广播地址（如 `192.168.1.255:47820`）发 `TOOK_DISCOVER`，对端回复 `TOOK_ANNOUNCE {deviceId, deviceName, protoVersion, autoPort}`。局域网内 **< 1 秒**完成，不需要知道对端 IP。
2. **广播无响应时退化为 TCP /24 扫描**（此时已知网段，扫描很快）。
3. **永远保留手动兜底**：手动输入 IP:端口，或二维码扫码。这是排查"为什么扫不到"时唯一能用的手段。

**坑 4 · 入站连接被防火墙拦**
- **Windows 端**：首次监听端口会弹"Windows 防火墙已阻止"，用户点了取消就再也扫不到。要主动做引导页；或在首次运行时用 `netsh advfirewall firewall add rule name="Took" dir=in action=allow protocol=TCP localport=47820` 静默放行（**需管理员权限，要做失败兜底**）。
- **Android 端**：监听端口需要应用在前台（或前台服务）。后台被冻结时对端找不到它 → 所以**同步应由用户在任一端主动发起**，而不是后台自动。
- **路由器 AP 隔离**（"访客网络"、部分酒店/公司 WiFi）会让同网段设备互相不可见。这个无解，只能提示用户换网络。

**一个容易忽略的现实问题**：PC 插网线、手机连 WiFi 时，如果路由器做了网段隔离或 PC 走了另一个 VLAN，扫描也会失败。UI 上要能显示"我的 IP / 网段 / 发现状态"，方便用户自己判断，比什么都不显示强。

## 10.2 整体架构

```
┌──────────────────────┐              ┌──────────────────────┐
│    PC (Electron)     │              │   Android (Java)     │
│                      │              │                      │
│  渲染进程: Vue 3     │              │  Activity + XML       │
│       ↕ IPC          │              │       ↕               │
│  主进程: Node        │              │  SyncService          │
│   ├ SQLite           │              │   ├ SQLite            │
│   ├ SyncServer (HTTP)│◀───────────▶│   ├ SyncServer (HTTP) │
│   ├ SyncClient       │   HTTP/JSON  │   ├ SyncClient        │
│   └ Discovery (UDP+TCP)             │   └ Discovery         │
└──────────────────────┘              └──────────────────────┘
```

**关键设计：两端完全对称。** 每端都同时实现 Server 和 Client，协议不区分主从。谁先发起谁当 Client。这样用户从 PC 点同步和从手机点同步，行为一致。

**同步一次 = 一次 HTTP 请求完成双向交换**（不要拆成 push + pull 两趟，中间失败会产生半同步状态）：

```
POST http://<对端IP>:47820/api/v1/sync
Headers:
  X-Took-Device: <deviceId>
  X-Took-Proto: 1
  X-Took-Nonce: <随机数>
  X-Took-Time: <毫秒时间戳>
  X-Took-Sign: HMAC-SHA256(sharedSecret, deviceId+nonce+time+bodyHash)

Body:  { "sinceRev": <上次同步的对端版本>, "changes": [ ...本端新增/修改的记录... ] }
Resp:  { "serverRev": <对端当前版本>, "changes": [ ...对端发来的记录... ], "applied": <条数> }
```

## 10.3 协议要点

- **端口**：固定一个高位端口（如 `47820`），两端一致。若被占用，Server 启动时用 `0` 让系统分配并写入广播包，Client 从 `TOOK_ANNOUNCE` 里读到实际端口 —— **广播发现本身就顺带解决了端口协商问题**，这是 UDP 广播优于纯扫描的另一个原因。
- **版本协商**：请求带 `protoVersion` 和 `schemaVersion`，不一致直接返回 426 并提示"两端版本不一致，请升级到同版本"。**这一步不能省**，否则一端的表结构变更会让另一端的解析器崩。
- **数据格式**：JSON。数据量极小（5 年任务 + 打卡 ≈ 几 MB），**MVP 直接全量交换，不做增量**。`sinceRev` 留字段但可以先传 0 走全量 —— 全量合并逻辑最简单、最不容易出 bug，等有性能问题再优化。这是一个值得刻意做的简化。
- **幂等**：同一批数据重复同步两次，结果必须完全一致。合并算法必须是幂等的（见下）。

## 10.4 验证与安全（这里不能省）

"扫到了就传"是危险设计 —— 同一个 WiFi 下（公司、咖啡厅、宿舍）任何人都能拉走你的任务和记事。

分两层：

**① 首次配对（一次性，人工确认）**

```
PC 发起 → 发现 Android → 请求配对
Android 弹出：PC「DESKTOP-XXX」请求配对，确认码 743 921
PC 端同时显示：      确认码 743 921
用户在两端核对一致后点确认 → 交换 deviceId + 生成 sharedSecret(32字节随机)
```

**确认码由两端各自用相同算法从配对挑战算出，用户只需肉眼比对**（类似蓝牙配对）。或者更省事：一端显示 6 位码，另一端输入。之后各自的 `knownPeers` 表里存 `deviceId + sharedSecret + 自定义备注名`，后续同步只验签、不再弹窗。

**② 后续同步（自动）**

每个请求带 HMAC-SHA256 签名 + nonce + 时间戳（时间戳超出 ±5 分钟拒绝，nonce 缓存防重放）。`/sync` 接口只接受已配对设备的签名，未配对一律 401。

**③ 传输加密（可选但建议）**

局域网明文 HTTP 在日常使用中可接受，但记事本内容属于隐私。**用 sharedSecret 派生 AES-256-GCM 密钥加密 payload 的成本很低（两端都是几十行）**，建议做上。**不要试图上 TLS** —— 自签证书的信任链在两端都要额外配置，收益不如对称加密。"配对 + 对称加密"对这个场景是性价比最高的组合。

## 10.5 合并与冲突

这是同步里唯一真正需要想清楚的部分。**每次修改必须打三个戳**：`updatedRev`（单调递增的本地版本号）、`updatedAt`（毫秒时间戳）、`deviceId`。

**合并规则（记录级 LWW，够用且行为可预测）：**

1. 记录不存在于任一侧 → 直接插入。
2. 只存在于一侧 → 插入另一侧。
3. 两侧都有 → 比 `updatedAt`，**大者胜**；**完全相等时按 `deviceId` 字典序取大者**（这一步保证两端算出相同结果，必须有）。
4. `deleted = 1` 的记录照常参与合并（**软删**）。绝不能硬删 —— 硬删掉的记录下次会被对端"复活"回来，这是同步类应用最经典的 bug。

**三条必须写进代码注释的约束：**

- **时钟偏差**：两端手机/电脑时间可能差几分钟。LWW 用 `updatedAt` 意味着"时间更快的设备永远赢"。缓解办法：每次同步成功后，把对端的 `updatedAt` 最大值记下，若本机时钟比它慢超过阈值就提示用户校准系统时间；或者在记录里存 `(updatedAt, deviceId, rev)` 三元组按顺序比较，`rev` 用 Lamport 计数（本地每次写递增，同步时取 `max(rev)+1`）—— **这个改动很小，能显著降低时钟问题**，建议直接做。
- **tombstone 清理**：软删记录永久堆积。策略：只清理"已同步给所有已知 peer 且超过 90 天"的墓碑。`knownPeers` 表里的 `lastSyncAt` 是清理的判据。
- **规则冲突要提示**：如果是两个设备的规则字段被各自改了（同一个 `startDate` / `weekdaysMask` 两边不同），LWW 会静默丢掉一边。**建议对重复规则字段做冲突检测**：检测到就保留两条记录并在 UI 上标"该任务在两端被同时修改"，让用户裁决。数据丢失比多一次点击更糟。

**打卡记录（Completion）例外**：它是"事实"而非"状态"，同一 `(taskId, occurDate)` 两端都标记为完成就是完成，没有冲突。可以直接 `INSERT OR IGNORE` / `ON CONFLICT DO UPDATE`，不走 LWW。这个区分让合并逻辑干净很多。

## 10.6 两端实现清单（工作量对齐）

| 模块 | PC (Node/TS) | Android (Java) |
|---|---|---|
| 本机网段计算 | `os.networkInterfaces()` + netmask→CIDR | `LinkProperties` |
| UDP 广播发现 | `node:dgram` | `DatagramSocket` + `MulticastLock` |
| TCP 端口探测 | `node:net` connect + 超时 | `Socket` + `ExecutorService` |
| HTTP 服务 | `node:http` | 内置 `ServerSocket` 手写，或嵌 **NanoHTTPD**（轻量，推荐） |
| 签名/加密 | `node:crypto` | `javax.crypto` / `java.security` |
| 本地库 | `better-sqlite3` | `SQLiteOpenHelper` 或 Room |
| 屏幕常驻引导 | 防火墙规则 / 提示 | 前台 Service + 电池优化白名单 |

**关键提醒：合并算法两端必须完全一致。** 两套独立实现最容易在这里分叉，产生"A 同步 3 次和 B 同步 3 次结果不同"的诡异 bug。做法：**写一组 JSON 测试向量**（含 20~30 组构造好的输入与期望输出：同时改、一删一改、时钟相同、时钟倒流、墓碑复活等场景），Node 和 Java 各写一个测试跑同一份 fixture，**两边都绿才算通过**。这个成本约半天，能省掉后期几天。

## 10.7 交互设计（容易被忽略但影响体验）

- 同步按钮点击后要有明确状态机：`扫描中 → 发现设备 → 等待确认 → 同步中 → 完成(N 条更新)`，每一步都要显示，否则用户点了没反应会重复点。
- 扫描超时要明确告知失败原因：**"未发现设备"要能区分是哪一种**（没配对过 / 网络不同 / 防火墙 / 对端没开应用），给不同提示。
- 公共 WiFi 下首次同步前提示"当前网络可能有其他设备"。
- **不要做后台定时自动同步**：移动端耗电、被系统杀、也没必要。改成"应用启动时 + 回到前台时 + 手动点击"三个时机。

## 10.8 一个更省事的替代方案（供权衡）

如果同步的用户就是你自己（或家人两三台设备），**用 Syncthing / 坚果云 同步一个导出的 `took-backup.json` 文件**，开发量不到自研同步的 1/10，可靠性还更高（文件级冲突有成熟的冲突副本机制）。

自研端口发现同步的价值在于"零配置、开箱即用"。**建议：MVP 先做 JSON 导出/导入（1 天工作量）保证数据不丢，把端口发现同步作为第二阶段。** 这样万一同步模块延期，产品也已经是可用的。

# 十二、最终方案（Tauri 2 + 自托管后端 + 整月网格卡片）

> **本节取代 §9~§11。** 约束已放开（不限语言）、同步改为服务端模式、卡片要求整月网格，三条都变了，前面的结论作废。

## 12.1 三条变化的连锁反应

| 你的新决定 | 带来的影响 |
|---|---|
| 技术栈放开，可用 Tauri 2 | PC 从 90~150MB 降到 8~15MB；**一套 Vue 覆盖 PC + Android**；但 Android 侧系统能力全部要靠自写 Kotlin 插件 |
| 同步拆成独立后端服务 | **§10 的整个 P2P 方案作废**：不需要 UDP 广播、不需要网段扫描、不需要配对确认、不需要两端对称实现。**合并逻辑从"写两遍"变成"只写一遍"** —— 这是本轮最大的收益 |
| 卡片必须整月网格 | RemoteViews 的控件限制成为硬约束，**这是全项目技术密度最高的一块**，需要专门设计（§12.4） |

**架构定稿：**

```
┌─────────────────────────┐        ┌─────────────────────────┐
│   PC (Tauri 2)          │        │  Android (Tauri 2)      │
│   ┌───────────────────┐ │        │  ┌───────────────────┐  │
│   │ Vue 3 前端（共享）  │ │        │  │ Vue 3 前端（共享）  │ │
│   └────────┬──────────┘ │        │  └────────┬──────────┘  │
│   ┌────────▼──────────┐ │        │  ┌────────▼──────────┐  │
│   │ Rust 核心 + SQLite │ │        │  │ Rust 核心 + SQLite │ │
│   └────────┬──────────┘ │        │  └────────┬──────────┘  │
│            │ 托盘/通知/自启        │           │ JNI          │
└────────────┼────────────┘        │  ┌────────▼──────────┐  │
             │                     │  │ Kotlin 插件层      │  │
             │                     │  │ 卡片/闹钟/保活/IPC  │  │
             │                     │  └───────────────────┘  │
             │                     └────────────┬────────────┘
             │      HTTP/JSON（可选，离线完全不影响）│
             └──────────────┬─────────────────────┘
                     ┌──────▼──────────┐
                     │  后端服务 (Go)   │
                     │  SQLite + 合并   │
                     │  自托管：NAS/云  │
                     └─────────────────┘
```

**"后端只做同步、其余功能不依赖后端"这个设计是对的**，而且正是业界主流的 **Local-first** 架构：本地库是唯一数据源，同步是可选的后台异步任务。网络不通、后端没起、忘了配地址 —— 应用全功能可用。这个决定要写进架构约束里，防止后续开发中不小心把业务逻辑挪到服务端。

## 12.2 Tauri 2 的现实成本（选它之前必须知道）

Tauri 2 的桌面端非常成熟，**Android 端是"能用"，不是"顺手"**。下面这张表决定排期：

| 能力 | Tauri 2 Android 支持 | 本项目是否要自写 Kotlin |
|---|---|---|
| 界面 / 日历视图 | WebView，完全没问题 | 否 |
| 本地 SQLite | `tauri-plugin-sql` 支持 | 否 |
| 系统通知 | `tauri-plugin-notification` | 否 |
| 文件读写 | 支持 | 否 |
| **桌面卡片（AppWidget）** | **无插件** | **是（必写，工作量最大）** |
| **定时闹钟（AlarmManager + 重启重建）** | **无插件** | **是** |
| **开机自启 / ROM 保活引导** | **无插件** | **是** |
| PC 托盘 / 开机自启 / 通知 | 核心支持 + 官方插件 | 否 |

**净结论：Android 侧要写约 1500~2500 行 Kotlin**（卡片 ~800 行、闹钟 ~400 行、保活引导 ~200 行、数据快照 IPC ~200 行）。

这仍然划算 —— 因为**卡片和闹钟无论换什么框架都必须写原生**，而 Tauri 帮你省掉的是整个界面层（一套 Vue 覆盖两端）。但别把"Tauri 2 支持 Android"理解成"配置一下就能跑"，这几块是要实打实投人的。

**Tauri 2 的四个风险，提前认领：**

1. **生态早期**：Android 侧遇到问题社区资料少，可能要一路查到 Rust 和 JNI 层。
2. **调试链路长**：Vue → Tauri IPC → Rust → JNI → Kotlin，出错时定位成本高。**建议第一步就搭一个"打通全链路"的最小 Demo 验证**（见 §12.7 的 P0），别等做到一半才发现某个环节不通。
3. **国内 WebView 碎片化**：华为/小米/OPPO 自研内核版本不一，日历网格用的是 CSS Grid，兼容性风险不高，但必须在这几家的真机上过一遍。
4. **打包流程**：Android 需要 NDK + 签名配置，CI 要提前搭，别留到最后。

> 如果后续 Android 变成主战场、卡片还要继续加功能，那时再评估 KMP + Compose Multiplatform（卡片零摩擦）。现在不必为此改变决定。

## 12.3 数据模型（最终版）

沿用 §9.1，补上同步所需字段：

```sql
-- 任务 / 记事 / 倒数日共用一张表，靠 kind 区分
CREATE TABLE item (
  id            TEXT PRIMARY KEY,        -- UUID
  kind          INTEGER NOT NULL,        -- 0=任务 1=记事 2=倒数日
  title         TEXT NOT NULL,
  content       TEXT,                    -- 记事正文；任务可为空
  anchor_date   TEXT NOT NULL,           -- 'YYYY-MM-DD'，LocalDate 语义
  end_date      TEXT,                    -- 区间结束日，单日时等于 anchor_date
  weekdays_mask INTEGER NOT NULL DEFAULT 0,  -- bit0=周一 … bit6=周日
  repeat        INTEGER NOT NULL DEFAULT 0,  -- 0不重复 1重复
  repeat_every  INTEGER,                 -- 配合 repeat：每 N 天/周
  repeat_until  TEXT,
  completion_mode INTEGER NOT NULL DEFAULT 0, -- 0逐日 1整段
  day_time      TEXT,                    -- 'HH:mm'，为空则全天
  remind_offset INTEGER DEFAULT -1,      -- -1 不提醒
  -- 同步必备三件套
  rev           INTEGER NOT NULL DEFAULT 0,  -- 服务端版本号
  updated_at    INTEGER NOT NULL,            -- 毫秒
  deleted       INTEGER NOT NULL DEFAULT 0,  -- 软删，永不硬删
  dirty         INTEGER NOT NULL DEFAULT 0   -- 本地未推送
);

CREATE TABLE completion (
  item_id     TEXT NOT NULL,
  occur_date  TEXT NOT NULL,
  status      INTEGER NOT NULL DEFAULT 0,
  rev         INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL,
  deleted     INTEGER NOT NULL DEFAULT 0,
  dirty       INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (item_id, occur_date)
);
```

两条铁律：

- **日期全部用 `'YYYY-MM-DD'` 字符串，不用时间戳。** 跨时区、夏令时、旅行时不会整片漂移一格。
- **删除一律软删（`deleted=1`），永不 `DELETE`。** 硬删的记录会被另一端同步回来"复活"，这是同步类应用最经典的 bug。

## 12.4 整月网格卡片（全项目最硬的一块）

你给的参考图是标准的中国式日历：**周一起始、7×6 网格、大字日期、下面一行小字**。要把小字从农历换成任务名，完全可行 —— 但 RemoteViews 有几个必须绕开的限制。

### 12.4.1 为什么不能用常规布局

`RemoteViews` 只支持一小撮控件，**没有 WebView、没有 RecyclerView、没有自定义 View、没有 Compose**。支持的是：
`LinearLayout`、`FrameLayout`、`RelativeLayout`、`GridLayout`(仅 API 31+)、`GridView`、`ListView`、`TextView`、`ImageView`、`ImageButton`、`Button`、`ProgressBar`、`ViewFlipper` 等。

三条路线：

| 路线 | 版本要求 | 复杂度 | 结论 |
|---|---|---|---|
| `GridLayout` 直接画 7×6 | **Android 12+ 才被 RemoteViews 支持** | 低 | 若 minSdk≥31 可用 |
| `GridView` + `RemoteViewsService.Factory` | 全版本 | 高（要写 Service、工厂、复用） | 过度设计 |
| **6 × `LinearLayout` 嵌套** | **全版本** | 低 | ✅ **推荐** |

**用纯 LinearLayout 嵌套就能画出网格**，不需要 GridView。结构：

```
LinearLayout(vertical)                    ← 根
├─ LinearLayout(horizontal)               ← 标题行「2026年10月」
├─ LinearLayout(horizontal)               ← 星期头「一二三四五六日」× 7
└─ LinearLayout(vertical)                 ← 6 周
    └─ LinearLayout(horizontal) × 6       ← 每一周
        └─ LinearLayout(vertical) × 7     ← 每一格
            ├─ TextView  日期（id=d1_date）
            └─ TextView  任务名（id=d1_task）
```

**View 数量约 142 个**（1 根 + 1 标题 + 7 星期 + 6 周 + 42 格 + 84 个 TextView）。RemoteViews 走 Binder 传输，约 1MB 上限，业界经验上限约 500 个 View —— 142 个完全安全，单次 `updateAppWidget` 耗时通常 20~50ms。

**每个 TextView 必须有唯一 ID**（`d1_date` … `d42_date`），因为 `setTextViewText(id, ...)` 要靠 ID 定位。这是样板代码，用脚本生成 `val ids = IntArray(42) { ... }` 即可，手写会漏。

### 12.4.2 能用的 setter（白名单，写错静默失效）

RemoteViews 只能反射调用标了 `@RemotableViewMethod` 的方法，用错不会有编译错误，只是**什么都不发生**：

| 需求 | 可行写法 |
|---|---|
| 设置文字 | `setTextViewText(id, "19")` ✅ |
| 设置颜色 | `setTextColor(id, color)` ✅ |
| 设置字号 | `setTextViewTextSize(id, COMPLEX_UNIT_SP, 13f)` ✅ |
| 设置背景（今日红圈） | `setInt(id, "setBackgroundResource", R.drawable.bg_today)` ✅ |
| 显示/隐藏 | `setViewVisibility(id, View.GONE)` ✅ |
| 设置加粗 | `setInt(id, "setTypeface", typeface)` ✅ 需传 Typeface 对象 |

### 12.4.3 三态渲染（按你的要求）

- **今天**：日期 TextView 挂红色圆形背景 `bg_today_circle`（对应参考图里的"19"红圈）
- **有任务 · 未完成**：任务文字 `#BDBDBD` 灰
- **有任务 · 已完成**：任务文字用主色高亮（如 `#FF6B35`）+ 可选加粗
- **无任务**：任务文字留空

**必须给任务 TextView 加 `singleLine="true"` + `ellipsize="end"`。** RemoteViews 里文字换行是把布局撑爆的最常见原因 —— 一旦换行，整行高度变化，下面几周的位置全乱。

### 12.4.4 最大的现实问题：高度不够

算一笔账：每格至少需要「日期 13sp + 任务 9sp + 内边距 ≈ 26dp」，6 行 = **156dp**；加标题行 + 星期头约 **40dp**，总共 **≈ 200dp**。

而一个 **4×5 的桌面卡片只有约 180dp 高** —— **装不下**。这是设计阶段就必须解决的问题，不是优化项。

三种解法，建议组合使用：

1. **默认按 5×5 或 6×5 设计**（约 300~360dp 高），空间充裕，也能放下任务名。
2. **提供两套布局**：标准版（显示任务名）+ 紧凑版（只显示彩色圆点指示有没有未完成任务），按实际高度自动切换。
3. **格子内只放 1 条任务**，多余显示 `+2`。一格里塞两行任务名，字号会小到看不清。

自动切换用 `onAppWidgetOptionsChanged()` 读 `OPTION_APPWIDGET_MIN_WIDTH/MIN_HEIGHT`，按阈值选布局并重新 `updateAppWidget`。同时声明：

```xml
android:resizeMode="horizontal|vertical"
android:minWidth="250dp" android:minHeight="180dp"
android:targetCellWidth="5" android:targetCellHeight="5"   <!-- Android 12+ -->
android:previewLayout="@layout/widget_preview"             <!-- 选择器里的预览图 -->
```

### 12.4.5 数据怎么喂给卡片（Tauri 最大的坑，要提前打通）

Tauri 的数据存在 Rust 侧（`tauri-plugin-sql` 管理的 SQLite），**Kotlin 插件读不到**。所以卡片不能自己去查数据库。

**正确做法：前端算好快照，通过 Tauri 命令写进 SharedPreferences，卡片只读 SharedPreferences。**

```
Vue 前端（数据变更 / 跨天 / widget onUpdate 触发时）
   ↓ invoke('update_widget_snapshot', { json })
Rust 命令 → JNI → Kotlin 插件
   ↓ prefs.edit().putString("snapshot", json).apply()
   ↓ AppWidgetManager.updateAppWidget(id, buildRemoteViews(json))
RemoteViews 渲染
```

快照只包含当月 42 天渲染所需的最小信息：

```json
{
  "month": "2026-10",
  "today": 19,
  "startWeekday": 4,
  "cells": [
    { "day": 28, "outMonth": true,  "text": "", "status": 0 },
    { "day": 19, "outMonth": false, "text": "健身", "status": 1 },
    { "day": 20, "outMonth": false, "text": "背单词", "status": 0 }
  ]
}
```

好处：卡片渲染 < 10ms、不依赖数据库迁移、App 进程被杀后卡片仍能正常刷新。**这条 IPC 链路建议在 P0 阶段就做一个最小 Demo 跑通**，它是整个方案里最容易在后期卡住的地方。

### 12.4.6 刷新时机

| 时机 | 手段 |
|---|---|
| 应用内数据变更 | 立刻写快照 + `updateAppWidget` |
| 跨天（第二天"今天"要换格子） | `updatePeriodMillis="1800000"`（30 分钟，是系统允许的最小值）+ 在 `onUpdate` 里用 `AlarmManager.set(RTC, 次日 00:00)` 兜一次精确刷新 |
| 用户增删卡片 | `onAppWidgetOptionsChanged` / `onEnabled` |
| 重启手机 | `BOOT_COMPLETED` 广播里重刷一次 |

跨天刷新用**非精确的 `AlarmManager.set()`**（差几分钟无所谓），可以避开 Android 12+ 的精确闹钟权限，这是个便宜的省事做法。

### 12.4.7 点击交互（你已明确卡片只预览）

打卡在 App 内完成，卡片只负责打开 App —— 这让实现简单很多，不需要在卡片里处理数据写入。

但建议做成 **点某一天 → 打开 App 并定位到那天**（每格一个 `PendingIntent`，`requestCode` 用日期序号，`extra` 带日期字符串）。42 个 PendingIntent 大约多占 4KB parcel，完全可接受。（Android 12+ 记得加 `FLAG_IMMUTABLE`。）

### 12.4.8 真机必测清单

- **国内 ROM 的 widget 缩放**：MIUI / HyperOS 会自行调整卡片尺寸，5×5 可能被拉成 4×6，布局必须能容错。
- **桌面网格密度**：启动器设成 6×6 网格时，widget 的实际 dp 尺寸会变。
- **深色模式**：Android 的 `values-night` 对 RemoteViews 生效，两套颜色都要给。
- **系统字体放大**：用户把字体调到最大时，13sp 会变成 ~20sp，直接撑爆。**这条几乎一定会踩**，要么用 `dp` 定位，要么在字体设置里做上限保护。
- **折叠屏展开/折叠**：尺寸变化会触发 `onAppWidgetOptionsChanged`，要保证不崩。

## 12.5 后端服务设计

### 12.5.1 选型：Go + SQLite，单文件可执行

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | **Go** | 单文件二进制、无运行时依赖、交叉编译一行命令、内存 < 30MB |
| 数据库 | SQLite（`modernc.org/sqlite`，纯 Go 无需 CGO） | 零运维，数据就是一个文件，备份=拷文件 |
| HTTP | 标准库 `net/http`（可选 `chi` 路由） | 依赖越少越好 |
| 分发 | 各平台单文件 + Docker 镜像 | 用户丢哪都能跑 |

不做 Node 的原因：需要用户装运行时或打包 node 二进制（体积翻倍）；不做 Rust 的原因：开发速度慢于 Go，而这个服务的逻辑就是合并，没有性能诉求。

### 12.5.2 只暴露一个业务接口

```
POST /api/v1/sync
Authorization: Bearer <token>

请求: {
  "deviceId": "uuid",
  "sinceRev": 12345,                    // 上次同步到的服务端版本，首次为 0
  "items":       [ ... 本地 dirty 的 item ... ],
  "completions": [ ... 本地 dirty 的 completion ... ]
}

响应: {
  "serverRev": 12400,                   // 本次同步后的服务端最新版本
  "items":       [ ... rev > sinceRev 的服务端记录 ... ],
  "completions": [ ... rev > sinceRev 的服务端记录 ... ],
  "conflicts":   [ { "id": "...", "reason": "rule_modified_both_sides" } ]
}
```

**一次请求完成双向交换**，不要拆成 push + pull 两趟 —— 中间失败会产生"推上去了但没拉回来"的半同步状态，很难排查。

辅助接口：

- `GET /api/v1/health` — 连通性测试，前端配置页用它验证地址
- `GET /api/v1/export` — 全量导出 JSON（备份用，也是"后端挂了数据还在"的保险）
- `GET /api/v1/rev` — 只查当前版本号，用于判断是否需要全量同步

### 12.5.3 合并逻辑只写一份（本轮最大收益）

前端不再实现任何合并算法，**只做两件事**：把 `dirty=1` 的记录推上去；把响应里的记录 `INSERT OR REPLACE` 进本地库、更新 `lastSyncRev`、清 `dirty`。

服务端合并规则：

1. **服务端为每条记录维护全局单调递增的 `rev`**（写入时 `rev = ++globalRev`）。
2. **冲突判定**：客户端推上来的记录，若其基线（`sinceRev` 之后服务端又改过同一条）→ 冲突。按 LWW 裁决：`updated_at` 大者胜；**完全相等时按 `deviceId` 字典序 tie-break**（保证多端算出相同结果，这一步不能省）。
3. **打卡记录不走 LWW**：它是"事实"不是"状态"，同一 `(item_id, occur_date)` 取 `status` 最大值 + `updated_at` 最大值即可，天然无冲突。这个区分让合并逻辑干净很多。
4. **规则字段冲突要上报**：如果 `anchor_date` / `weekdays_mask` / `repeat` 这三个字段两端都改过，LWW 会静默丢掉一边。这种情况把记录放进 `conflicts` 返回，前端提示"该任务在两端被同时修改"，让用户裁决。**数据静默丢失比多一次点击糟糕得多。**

### 12.5.4 离线与失败处理

- 同步是后台异步任务，**失败绝不阻塞 UI**，也绝不覆盖本地数据。
- `dirty` 标记保证：推失败的数据下次接着推，不会丢。
- 同步状态在 UI 上要有明确呈现：`未配置 / 同步中 / 已同步（3 分钟前）/ 失败：无法连接`。
- **首次接入时做一次"本地 vs 服务端"差异预览**，让用户确认方向（万一误配到一个有旧数据的后端，能看到会覆盖什么）。

### 12.5.5 部署与安全

三种部署形态，都在支持范围内：

1. **局域网常开设备**（NAS / 树莓派 / 家里 PC）— 最私密，但手机出门不同步。
2. **云服务器 + 域名**（推荐）— 手机在外面也能同步。
3. **Docker** — 一条 `docker run` 搞定，适合 NAS 用户。

安全清单：

- **单 Bearer Token** 认证，服务首次启动自动生成并打印，配置页可重置。令牌即数据，泄露即全丢，前端配置页要写明。
- **公网必须 HTTPS**（Caddy 自动证书 / Nginx + certbot / Cloudflare Tunnel 都可以）。局域网内 HTTP 可接受。
- 服务端**不存明文密码、不做多用户** —— 单用户自托管，不做账号体系。这是刻意的简化，别加。
- 记得：Token 只放 Header，不要放 URL 查询串（会进日志）。

### 12.5.6 前端配置页

需要四个字段就够：`服务地址`、`Token`、`设备名`、`自动同步开关`。加一个"测试连接"按钮（打 `/health`）。

## 12.6 数据流总览（确认"不依赖后端也能跑"）

| 功能 | 依赖本地库 | 依赖后端 |
|---|---|---|
| 月历首页、任务增删改、重复规则展开 | ✅ | ❌ |
| 打卡 / 撤销打卡 | ✅ | ❌ |
| 记事、倒数日 | ✅ | ❌ |

## 12.8 这一轮剩余的待确认

1. **打卡粒度**：「周一~周三」是三天各自打卡，还是整段一次？（建议做成创建时的选项，默认逐日 —— 一个字段的事，别留到后期）
2. **卡片尺寸基线**：默认按 5×5 设计可以接受吗？还是必须保证 4×5 也能放得下任务名（那样字号会小到 8sp 左右，可能需要砍掉任务名只显示色点）。
3. **后端部署在哪**：局域网常开设备，还是云服务器？（决定要不要做 HTTPS 和域名引导）
4. **小时级重复是否必须**？（决定要不要申请精确闹钟权限、以及上架时要不要写用途说明）
