**PC = Tauri 2 + Vue 3；Android = 原生 Kotlin（Compose + Glance）；后端 = Go 单文件服务，两端共用一个，只做数据合并。**

## 3. 数据模型

### 3.1 核心概念：命中日 vs 周期

拆成两个互不相干的维度，这是理解整个模型的关键：

- **命中日（occurrence）**：这条任务在**哪些日子**的格子里出现。由"选了周几 / 哪一段日期"决定。
- **周期（period）**：这条任务的打卡**归到哪一次**。一个周期内只打卡一次，**周期内所有命中日共享同一个状态**。

用你的例子（2026 年第 43 周）。下文的 A、B 指**同一条规则下的两个任务**，它们共享规则的重复与提醒、各自独立打卡：

```
任务 A：勾选 周一~周五，每周重复
  命中日 = 10/19(一) 10/20(二) 10/21(三) 10/22(四) 10/23(五)
  本周周期 = 10/19 ~ 10/23 这一次 → 周期标识 = 10/19

任务 B：勾选 周一、周五，每周重复
  命中日 = 10/19(一) 10/23(五)        ← 周二三四没有 B
  本周周期 = 同一个周期 → 周期标识 = 10/19

日历上的样子：
  周一 10/19   A ✗   B ✗      ← 两个任务，都未完成
  周二 10/20   A ✗            ← 只有 A
  周三 10/21   A ✗
  周四 10/22   A ✗
  周五 10/23   A ✗   B ✗

周一把 A 打了卡 →
  周一 A ✓  周二 A ✓  周三 A ✓  周四 A ✓  周五 A ✓
  ↑ 五个格子全部变成"已完成"，但文字都还在，一个字都没消失
  B 不受影响，仍然是 ✗

周二打开，觉得 B 也做了 → 在周二或周五任意一格点 B
  （也可以直接在周五点，反正 B 本周还没完成）
  周一 B ✓  周五 B ✓   ← B 的两个命中日同时变已完成
```

**五条语义（写进验收清单）：**

1. **一个任务是"整体的一件事"，不是每天一条。** 周一~周五是"这件事这周要做"，不是五件分开的事。
2. **一个周期内只打卡一次，作用于该周期全部命中日。** 周一打完，周二到周五全部同步变已完成。
3. **不强制在某一天完成。** 周一~周五任意一个命中日点打卡都算数，效果完全一样 —— 这正是"不强制要求必须做那一条"的含义。
4. **完成后永远保留显示。** 只变样式，不隐藏、不删除、不划掉。
5. **没勾选的日子不出现。** B 只在周一和周五露面。

> **历史修正**：我先后提过"逐日独立打卡"和"整段首尾包住"两个错误模型。前者把 A 拆成了五件事，后者把 B 的周二三四也显示了出来。现在这版把"显示哪些天"（命中日）和"打卡算一次"（周期）分开，两个例子才同时成立。

### 3.2 周期怎么切

| 规则 | 周期边界 | 周期标识 `period_start` |
|---|---|---|
| 每周固定几天（`repeat_mode=weekly`, `weekdays_mask≠0`） | **每个自然周**（周一~周日） | 该自然周的**周一** |
| 每 N 天（`repeat_mode=every`, `repeat_every=N`） | 从 `start_date` 起，每 N 天一个周期 | `start_date + k*N` |
| 每月某日（`repeat_mode=monthly`） | **一个周期 = 一天**，就是那天本身 | 那天本身 |
| 每年某月某日（`repeat_mode=yearly`） | **一个周期 = 一天**，就是那天本身 | 那天本身 |
| 不重复（`repeat_mode=none`） | **整个规则只有一个周期**，从头到尾 | `start_date` |

> `period_start` 取「自然周的周一」而不是「本周第一个命中日」。原因是：用户中途改了勾选的星期几时，周一是稳定不变的锚点，历史打卡记录不会因为改规则而错位。B 只勾周一和周五，它的周期标识同样是那一周的周一。

**按月、按年的两种规则，周期划分同样是「一天」：**

- **每月某日**：一个周期 = 一天，`period_start` 就是那天本身。`month_day=31` 时，小月落在该月最后一天（4 月落 4/30、2 月落 2/28 或 2/29）。
- **每年某月某日**：一个周期 = 一天，`period_start` 就是那天本身。2/29 在平年落在 2/28。

### 3.3 命中日判定

判定某个日期 `d` 是否显示某任务：

```
1. d < start_date                          → 不显示
2. repeat_until 非空 且 d > repeat_until   → 不显示
3. repeat_mode = weekly（weekdays_mask ≠ 0）：
       d 的星期几（周一=bit0）在 mask 中命中 → 显示
4. repeat_mode = every（repeat_every = N）：
       floor((d - start_date) / N) 对应的区间内 → 显示
5. repeat_mode = monthly（month_day = M）：
       d 的日 == 该年该月的钳制日(M) → 显示
6. repeat_mode = yearly（year_month, year_day）：
       d 的月 == year_month 且 d 的日 == 该年该月的钳制日(year_day) → 显示
7. repeat_mode = none：
       start_date ~ end_date 之间 → 显示
```

**月末钳制与闰年规则（第 5、6 条里的「钳制日」）：** `month_day` 允许 1~31（-1 = 每月最后一天），`year_day` 允许 1~31。当设定的日号超过当月实际天数时，一律**钳到该月的最后一天**，绝不"这个月跳过"：`month_day=31` 时 4 月落 4/30、2 月落 2/28 或 2/29；`year_month=2, year_day=29` 时平年落 2/28、闰年落 2/29。钳制只决定「这一次落哪天」，不改用户填的值 —— 下个大月仍然回到 31 日。

**命中日由规则算出，不落表**；**周期状态落在 completion 表，一个周期一行**。

举例：

| 配置 | 命中日 | 每周期的打卡次数 |
|---|---|---|
| A：周一~周五，每周重复 | 每周一~五共 5 天 | 每周 1 次 |
| B：周一、周五，每周重复 | 每周一、周五共 2 天 | 每周 1 次 |
| C：10/01~10/05，不重复 | 只有这 5 天 | 整个任务 1 次 |
| D：`repeat_mode=every, repeat_every=7, start_date=10/01, end_date=10/03` | 10/01~03、10/08~10、10/15~17… | 每一段 1 次 |
| E：每月 31 日 | 大月 31 日；小月落月末（4/30、2/28 或 2/29） | 每月 1 次 |
| F：每年 2/29 | 闰年 2/29；平年落 2/28 | 每年 1 次 |

### 3.4 一个必须提前想清楚的设计后果

**完成任务不消失 + 一天可能挂多个任务 = 格子会越来越满。**

一个格子可用宽度约 40dp（手机卡片），只放得下 1 条任务名。你举的例子周一就有 A 和 B 两条，实际用起来一天三五条很常见。

所以格子内必须有取舍规则，按尺寸三档走（§5.5、§6.2.1）：

1. **小尺寸**：只显示未完成任务，溢出 `+N`，完成痕迹用小圆点保留
2. **中尺寸**：未完成优先，剩余位置显示已完成，最多 2 条
3. **大尺寸**：尽量都显示，最多 3~4 条 + `+N`

卡片不是任务清单，是"一眼看今天还要做什么"的仪表盘。这个取舍要提前接受。

### 3.5 表结构

```sql
-- 规则：承载重复方式 / 时间范围 / 提醒，是所有任务共享的基础条件
CREATE TABLE rule (
  id            TEXT PRIMARY KEY,           -- UUID
  title         TEXT NOT NULL,
  enabled       INTEGER NOT NULL DEFAULT 1,
  repeat_mode   INTEGER NOT NULL,           -- 0=weekly 1=every 2=monthly 3=yearly 4=none
  weekdays_mask INTEGER NOT NULL DEFAULT 0, -- repeat_mode=weekly 时用，bit0=周一 … bit6=周日
  repeat_every  INTEGER,                    -- repeat_mode=every 时用，1..3660
  month_day     INTEGER,                    -- repeat_mode=monthly 时用，1..31；-1 表示「每月最后一天」
  year_month    INTEGER,                    -- repeat_mode=yearly 时用，1..12
  year_day      INTEGER,                    -- repeat_mode=yearly 时用，1..31
  start_date    TEXT NOT NULL,              -- 'YYYY-MM-DD'（LocalDate 语义，不用时间戳）
  end_date      TEXT,                       -- 空=不限
  repeat_until  TEXT,                       -- 重复终止日，空=永久
  -- 提醒配置挂在独立的 reminder 表上（owner_kind=0），见 §6.3.1
  -- 同步三件套
  rev           INTEGER NOT NULL DEFAULT 0, -- 服务端版本号
  updated_at    INTEGER NOT NULL,           -- 毫秒
  deleted       INTEGER NOT NULL DEFAULT 0, -- 软删，永不物理删
  dirty         INTEGER NOT NULL DEFAULT 0  -- 本地未推送
);

-- 任务：只是规则下的一个名字，打卡以任务为单位
CREATE TABLE task (
  id          TEXT PRIMARY KEY,             -- UUID
  rule_id     TEXT NOT NULL REFERENCES rule(id),
  title       TEXT NOT NULL,
  enabled     INTEGER NOT NULL DEFAULT 1,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  -- 同步三件套（含义同上）
  rev         INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL,
  deleted     INTEGER NOT NULL DEFAULT 0,
  dirty       INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_task_rule ON task(rule_id);

-- 打卡：一个周期一行，作用于该周期的全部命中日；周期仍由所属规则算出（§3.2）
CREATE TABLE completion (
  task_id       TEXT NOT NULL,
  period_start  TEXT NOT NULL,               -- 'YYYY-MM-DD'，周期标识（见 §3.2）
  status        INTEGER NOT NULL DEFAULT 0,  -- 0=未完成 1=已完成
  rev           INTEGER NOT NULL DEFAULT 0,
  updated_at    INTEGER NOT NULL,
  deleted       INTEGER NOT NULL DEFAULT 0,
  dirty         INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (task_id, period_start)
);

CREATE INDEX idx_completion_period ON completion(period_start);
```

```sql
-- 记事 / 倒数日 / 笔记本仍是一张独立表，不挂规则下
CREATE TABLE memo (
  id          TEXT PRIMARY KEY,              -- UUID
  kind        INTEGER NOT NULL,              -- 0=记事 1=倒数日 2=笔记本
  title       TEXT NOT NULL,
  content     TEXT,                          -- 记事正文 / 倒数日备注 / 笔记本正文
  start_date  TEXT,                          -- 记事：可空（空=不排期）；倒数日：目标日；笔记本：不用
  end_date    TEXT,                          -- 记事：时间段结束，空=单日
  category    TEXT,                          -- 仅笔记本使用；分类名由用户自建，默认 '未分类'，排序按创建顺序，不做颜色
  -- 同步三件套（含义同上）
  rev         INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL,
  deleted     INTEGER NOT NULL DEFAULT 0,
  dirty       INTEGER NOT NULL DEFAULT 0
);
```

**「没有打卡记录」= 该周期未完成**，不需要为未完成状态写行。一条永久重复的任务一年只写 52 行。

**为什么拆成 rule + task：** 用户的心智模型是「先建规则（定重复与提醒），再给规则加任务」—— 一个规则下可以有多个任务，它们共享重复与提醒、但各自独立打卡。单表 `item` 表达不了这层从属关系：要么把重复字段在每个任务上复制一遍（改一次重复方式要改 N 行，历史打卡极易错位），要么把任务压成规则的一个附属字段（一个规则就只能有一个任务）。拆成两级后，改重复只动 `rule` 一行，`task` 与 `completion` 一动不动，同步粒度也自然对齐到「规则 / 任务 / 打卡」三层。

### 3.6 三条硬约束

1. **日期一律用 `'YYYY-MM-DD'` 字符串。** 存 epoch 毫秒会在跨时区、旅行、夏令时场景下整片日期漂移一格，且极难排查。
2. **删除一律软删（`deleted=1`），永不 `DELETE`。** 硬删的记录会被另一端同步回来"复活"，这是同步类应用最经典的 bug。
3. **改规则只影响未来，历史打卡记录不动。** 用户改一次重复规则就洗掉上个月的记录，是这类应用最典型的翻车方式。实现上：修改规则时把旧 `rule` 的 `repeat_until` 写成「昨天」，再插入一条新 `rule`，旧记录自然保留。两级结构下具体是：**旧 `rule` 置 `repeat_until=昨天` 后，它下面的 `task` 与 `completion` 原样保留** —— 历史打卡不会因为规则换代而消失，这些任务只是不再产生新的命中日；新规则另建一条 `rule`，原任务若需延续，由用户在编辑界面选择「复制到新规则」，是显式动作，不静默搬家。

### 3.7 统计口径

按**周期**算，不按天算：

- 本月完成率 = 本月内「已完成周期数 ÷ 应出现周期数」
- 单任务完成率 = 该任务已完成周期数 ÷ 已展开周期数
- 连续天数 = 从今天往前数，连续"当天所有命中任务所在周期都已完成"的天数

**A + B 在一周内应完成 2 次，不是 7 次。** 周一做完 A，这一周的 A 就永远是完成态，不会因为周二三四没再点而掉回去。

**统计必须是真实计算，不允许写死。** 规则级完成率 = Σ(其下每个任务已打卡周期) ÷ Σ(其下每个任务应完成周期)；界面上「已完成周期」这个总数必须严格等于明细表「已完成」列的合计 —— 两个数字对不上，就是造假而不是统计。

### 3.8 倒数日的模型

倒数日落在 `memo` 表（`kind=1`），**不挂规则、不走重复逻辑**，也进不了日历的命中日展开：

| 字段 | 倒数日里的含义 |
|---|---|
| `title` | 卡片左上角显示的名字，如"纪念日"（必填） |
| `start_date` | **目标日期**（必填） |
| `content` | 备注，可选 |
| `end_date` / `category` | 不使用（`end_date` 只服务记事的时间段，`category` 只服务笔记本） |
| `kind` | 固定为 `1`，由所在分区决定，表单里不出现 |

天数计算：

```
delta = ChronoUnit.DAYS.between(targetDate, today)

delta > 0  → 还有 delta 天
delta = 0  → 就是今天
delta < 0  → 已经 |delta| 天
```

你举的例子：目标 2025-10-19，今天 2026-10-19，`delta = -365` → 显示「已经 365 天」。

**提醒挂在 `reminder` 表上**，用 `offset_days` 表达"还剩 N 天时提醒"：

| 配置 | 含义 |
|---|---|
| `offset_days=0, time=09:00` | 当天早上 9 点提醒 |
| `offset_days=7, time=20:00` | 剩 7 天时晚上 8 点提醒 |
| 多条组合 | 剩 30 / 7 / 1 / 0 天各一条，每个独立选通知还是闹钟 |

对已经过去的日期（`delta < 0`），"提前 N 天"没有意义 —— 这类只允许"当天提醒"或"每年同日提醒"（如果以后要做周年纪念的话）。

## 4. 重复规则：展开与查询

规则本身**不预生成实体行**（"永久重复"会写出无限数据）。月视图查询流程：

```
查某月 42 天（含前后月补格）
  → ① 取该月可见范围内所有未删除的 rule 及其下未删除的 task
  →    对每条 rule 逐日跑 §3.3 的命中判定，得到「(日期, ruleId)」命中集合
  →    对每个 (日期, ruleId) 算出它属于哪个周期（§3.2），得到 periodStart
  →    把该 rule 的命中日摊到它下面每个 task 上，得到「(日期, taskId)」
  → ② 按 task 逐条 LEFT JOIN completion ON (task_id, period_start) 拿状态
  → 按日期分组渲染
```

规则算「哪些天出现」，任务带「打没打卡」—— 两级分开之后，改重复只跑第①步，打卡只碰第②步。

要点：**同一条任务在同一个周期的不同命中日，查到的是同一行**。这正是"A 周一打卡，周二到周五也显示已完成"的实现方式 —— 不是写了五行，是五天的格子查了同一行的同一个状态。

举例渲染 2026-10-19 和 10-20：

```
2026-10-19 周一
  任务A → 周期 10/19 → completion(A, 2026-10-19) status=1 → 已完成 ✓
  任务B → 周期 10/19 → completion(B, 2026-10-19) 无行     → 未完成 ✗

2026-10-20 周二
  任务A → 周期 10/19 → completion(A, 2026-10-19) status=1 → 已完成 ✓
  （B 在周二没有命中，不出现）

2026-10-23 周五
  任务A → 周期 10/19 → 已完成 ✓        ← 和周一查到的是同一行
  任务B → 周期 10/19 → 未完成 ✗        ← 和周一查到的也是同一行
```

为性能考虑，实现上做两件事：

- **结果缓存**：按 `(ruleId, 规则指纹)` 缓存"该规则在查询窗口内的命中日期集合 + 各自周期"，**规则字段变更时失效**；任务增删（`task` 行新增/删除/换 `rule_id`）时同样必须失效 —— 命中日没变，但摊出来的 (日期, taskId) 集合变了，缓存不失效就会漏显示或显示已删任务。
- **窗口限制**：查询范围限制在 `[本月-1, 本月+1]`，不做无限展开。

**提醒排程是唯一的例外**：需要在未来 90 天内为每一天的 `day_time` 注册闹钟，这部分要落一张 `reminder_schedule(reminder_id, task_id, occur_date, fire_at, snooze_until)` 表，跨天时滚动补充。排程行只引用 `reminder.id`，**不冗余任何提醒方式字段** —— 发通知还是响闹钟由 `reminder.notify_on` / `alarm_on` 决定；规则级提醒（`owner_kind=0`）摊到该规则下每个任务的每个命中日。

> 提醒按**命中日**注册，但一个周期只需要响一次 —— 建议默认只在**该周期的第一个命中日**提醒（周一~周五的任务在周一提醒一次就够了）。如果用户想每天都被提醒，做成**规则级开关**（`repeat_rule`），规则下的任务继承。

### 4.1 展开与打卡引擎要跑通的边界用例

规则判定看起来简单，但跨月、月末、闰年是 bug 高发区。建议 P0 阶段用 20~25 组用例先跑通，比写 UI 早一天定死就少一天返工：

| 用例 | 期望 |
|---|---|
| A：周一~周五，周一打卡 | 周一~周五五格全部显示已完成，且**只有一条** completion 行 |
| B：周一 + 周五，周一打卡 | 周一、周五两格已完成；周二三四不出现 B |
| `repeat_mode=weekly`，`weekdays_mask` = 周一\|周五，跨月 | 每月正确命中所有周一和周五，不串月 |
| 同一周跨月（如 10/31 周五、11/01 周六） | A 勾周一~周五时，10/31 和 11/01 分属**不同周期**，各自独立打卡 |
| `repeat_mode=every`，`repeat_every=7`，`start_date=1/29`（闰年） | 2/29 是否命中；平年 3/1 如何处理 |
| `start_date > end_date` | 视为非法配置，创建时就拒绝 |
| `repeat_until` < `start_date` | 视为无周期，创建时警告 |
| `repeat_mode=weekly`，`weekdays_mask` = 周日的任务，周起始日设为周一/周日 | 命中结果必须一致（周起始日只影响渲染，不影响判定与周期划分） |
| 一天内同时命中 A 和 B | 两条任务独立显示，各自状态互不影响 |
| 打卡后再取消 | 该周期回到未完成，所有命中日同步变回灰色 |
| 夏令时切换日 | 因为它只影响 `LocalDate`，不应有任何影响 —— 若有，说明误用了时间戳 |
| G：`repeat_mode=monthly`，`month_day=31`，跨 2/4/6/9 月 | 落在各月最后一天（2/28 或 2/29、4/30、6/30、9/30）；用户填的 31 **不被改写**，下个大月仍回到 31 日 |
| H：`repeat_mode=monthly`，`month_day=-1`，跨闰年 2 月 | 闰年落 2/29，平年落 2/28；其余月份落各自最后一天 |
| I：`repeat_mode=yearly`，`year_month=2`，`year_day=29` | 平年落 2/28，闰年落 2/29；非闰年的 3/1 **不命中**（钳制不溢出到下个月） |

**"同一周跨月"这条容易被漏掉**：周期以自然周（周一~周日）为单位，而月视图按月切。10/31 是周五、11/01 是周六，它们在同一自然周但在不同月份。如果周期标识用了"该月第一个命中日"就会算错，必须用"该自然周的周一"（§3.2）。

## 5. PC 端（Tauri 2）

### 5.1 贴进桌面壁纸层（WorkerW）—— 已确认要做

需求已明确：**像 Windows 小部件那样，被普通窗口覆盖、`Win+D` 后仍然可见、跟壁纸一起显示/隐藏。** 这就是 WorkerW 方案，必须自己调 Win32，Tauri 没有现成插件。

#### 能力对照

| 需求 | 支持情况 | 工作量 |
|---|---|---|
| 贴进桌面壁纸层（WorkerW） | ⚠️ 自己调 Win32 | **3~5 天**（含调试与兼容适配） |
| 无边框 / 透明背景 | ✅ `decorations:false` / `transparent:true` | 无 |
| 不在任务栏、不出现在 Alt+Tab | ✅ `skipTaskbar:true` + `WS_EX_TOOLWINDOW` | 无 |
| 托盘图标 | ✅ Tauri Tray | 无 |
| 开机自启 | ✅ `tauri-plugin-autostart` | 无 |
| 系统通知 | ✅ `tauri-plugin-notification` | 无 |
| 全局快捷键（呼出主窗口） | ✅ `tauri-plugin-global-shortcut` | 无 |

#### 实现步骤（Rust + `windows` crate）

```
1. win32::FindWindowA(wc!("Progman"), None)                    → 拿 Progman
2. SendMessageTimeout(progman, 0x052C, 0x0D, 0, ...)          → 让系统生成 WorkerW
3. EnumWindows 遍历：
     对每个顶层窗口 w，EnumChildWindows 找 "SHELLDLL_DefView"
     若找到，则 FindWindowExA(None, Some(w), wc!("WorkerW"), None) 得到目标 WorkerW
4. SetParent(tauri_hwnd, workerW)
5. 调整子窗口样式：去掉 WS_POPUP 边框 → 保留 WS_CHILD；
   加 WS_EX_TOOLWINDOW 避免出现在 Alt+Tab
6. 用 GetClientRect(workerW) 拿桌面尺寸，把窗口尺寸/位置对齐
```

约 **150~250 行 Rust**，逻辑不复杂，**复杂的是边界情况和版本差异**。

#### 六个已知坑（这些才是这 3~5 天的真实来源）

1. **Win11 24H2 改了 WorkerW 结构。** 24H2 之后 `Progman` 下直接挂着 `SHELLDLL_DefView`，不再有独立的 WorkerW 兄弟窗口。探测失败时要**自动降级**为"普通置顶窗口 + 托盘"，否则功能在部分用户机器上直接不可用。必须做版本探测（`RtlGetVersion`）。
2. **Explorer 崩溃或用户重启资源管理器** → WorkerW 被销毁，我们的窗口变成孤儿（不可见）。必须监听 `TaskbarCreated` 消息或轮询 `IsWindow(workerW)`，失效后自动重新附着。
3. **Wallpaper Engine / 动态壁纸软件也抢 WorkerW。** 两者会冲突，可能需要"关闭动态壁纸才生效"的提示，或做在层级里共存的处理。
4. **多显示器。** 每个显示器有各自的 WorkerW。要先拿到目标显示器的 rect 再去匹配对应的 WorkerW，不能只取第一个。
5. **`SetParent` 会改变坐标系。** 之后窗口坐标变成相对父窗口，Tauri 自己的 `set_position` 语义会变，位置计算要全部改用桌面坐标手动处理。
6. **窗口生命周期错位。** Tauri 管理着窗口，`SetParent` 之后 Tauri 的部分窗口操作（`setAlwaysOnTop`、`setFullscreen`、`show/hide`）行为会异常。**建议这条链路完全绕过 Tauri 的窗口 API**：Tauri 只负责创建窗口，之后所有 Win32 操作由我们自己封装一层，Tauri 侧不碰。

#### 建议的分层架构

```rust
// src-tauri/src/desktop_pin.rs
pub enum PinMode { WorkerW, FallbackAlwaysOnTop, Disabled }
pub fn attach_to_desktop(hwnd: HWND) -> PinMode   // 探测→附着→失败降级
pub fn watch(&self)                                 // 监视 Explorer 重启并重附着
pub fn detach(&self)                                // 恢复为普通窗口（设置里可关）
```

用户设置里给三档：**贴桌面壁纸 / 普通置顶窗口 / 普通窗口**。默认"贴桌面壁纸"，探测失败自动降级并提示一次。

> **务必分配独立的验证时间**：这块功能必须在 Win10、Win11 23H2、Win11 24H2 三个版本上真机验证，虚拟机测不出 WorkerW 的真实行为。

### 5.2 主窗口形态建议

- 默认启动到托盘，点击托盘图标弹出日历窗口（符合日程类工具习惯）
- 关闭窗口 = 隐藏到托盘，不退出（要在设置里给"退出"入口）
- 启动时是否自动显示，做成设置项

窗口外观三项（对应 §11 已确认清单）：

| 能力 | 行为 |
|---|---|
| **整体透明度** | 设置里 40%~100% 连续可调。**只作用于窗口底色**，卡片本身与文字不透明 —— 否则月历格子会随着透明度一起糊掉，可读性直接崩 |
| **吸附屏幕边缘** | 拖到屏幕某条边附近自动贴齐。吸附之后**对应那一侧的圆角压平**，窗口看起来是从边上长出来的，而不是浮着一个圆角矩形 |

### 5.3.1 PC 端的提醒（与 Android 对等）

PC 也要实现同一套通知 / 闹钟 / 贪睡，否则"提醒"这个功能在两端行为不一致会让人困惑。实现映射：

| 能力 | Android | PC（Tauri） |
|---|---|---|
| 精确调度 | `AlarmManager.setAlarmClock` | Rust 侧 `tokio::time` 定时器 + 常驻主进程 |
| 普通通知 | NotificationManager | `tauri-plugin-notification`（Windows Toast / macOS 通知中心） |
| 闹钟（强提醒） | 全屏 Activity + 响铃 | **新建一个置顶无边框窗口 + 播放音频 + 托盘闪烁** |
| 贪睡 | 重设 AlarmManager | 重设定时器 |
| 重启恢复 | `BOOT_COMPLETED` | 启动时扫 `reminder_schedule` 重建定时器 |

**两个 PC 特有的坑：**

1. **Windows 睡眠后定时器不可靠。** 合盖休眠期间 `tokio` 的定时器不会推进。做法：定时器只作短周期唤醒用，真正的判断靠**每分钟轮询一次"现在应该响什么"**（时间漂移自愈），加上系统唤醒事件重置。这也顺带解决了"睡过点"的问题 —— 醒来后把错过的提醒补弹出来。
2. **常驻内存开销。** Tauri 主进程常驻（托盘），内存约 40~80MB，可接受；但**别把 Vue 窗口一直挂着**，关窗即销毁，靠托盘和 Rust 定时器维持。

"闹钟"在 PC 上的表现建议：置顶窗口 + 响亮提示音 + 托盘图标闪动，而不是全屏 —— 全屏在 PC 上太暴力，用户可能正在开会。

### 5.5 按窗口大小决定内容密度

PC 端和 Android 卡片用**同一套断点语义**：小窗口只留未完成，大窗口显示多条。这样用户在两端看到的信息优先级一致。

| 窗口宽度 | 档位 | 格子内容 | 每格任务数 | 说明 |
|---|---|---|---|---|
| < 720px | **紧凑** | 只显示**未完成任务** | 1 条 + `+N` | 左下角一排小圆点保留完成痕迹 |
| 720~1080px | **标准** | 未完成优先，剩余位置显示已完成 | 最多 2 条 | 已完成用主色加粗 |
| > 1080px | **宽松** | 全部显示 | 最多 4 条 + `+N` | 字号可放大 1px |

实现方式：

- 用 CSS Container Queries（`@container (min-width: 720px)`）或 `ResizeObserver` 驱动一个 `density` 状态，`DayCell` 按它决定渲染几条。
- 窗口最小宽度限制到 **600px**（`minWidth: 600`），再窄月历格子就没法看了。低于 600 时提示用户，不强行压缩。
- 贴桌面壁纸层时，窗口尺寸是用户拖的 —— 响应式在这时候才是真需求，所以**不要用固定像素布局**。

**一个附加建议：给"桌面小部件模式"做一组预设尺寸**（如 420×560 竖条、900×420 横向）。用户从设置里一点就切到合适大小并贴进壁纸层，比让他自己拖到刚好舒服省事得多。这也是 Tauri 的 `setSize` 一行调用。

## 6. Android 端（原生 Kotlin）

### 6.1 改用原生的判断是对的

卡片是核心卖点且后续会持续加功能，那 Android 侧迟早要深度写原生代码。用 Tauri 的话等于"Web 壳 + 一堆 Kotlin 插件"，两套心智模型叠加，调试链路还长（Vue → IPC → Rust → JNI → Kotlin）。**直接原生，卡片/闹钟/保活全是一等公民，没有中间层。**

代价要认：**月历、任务编辑、设置这几套 UI 要写两遍**（Vue 一遍 + Compose 一遍）。约增加 1.5~2 周工作量。这是为卡片自由度和原生体验付的价，值得。

### 6.2 整月网格卡片（Glance）

#### 布局结构

```
Column
├─ Row     标题行「2026年10月」
├─ Row     星期头「一 二 三 四 五 六 日」
└─ Column  6 周
    └─ Row × 6        每周
        └─ Column × 7 每格
            ├─ Text  日期（13sp）
            └─ Text  任务名（9sp，单行省略）
```

对应 Glance 代码大致是三层 `repeat` 嵌套，**约 40 行**。对比手写 RemoteViews 要维护 84 个 TextView ID（`d1_date` … `d42_task`），差距是量级的。

**View 总量约 130~142 个。** RemoteViews 走 Binder 传输约 1MB 上限，业界经验上限 ~500 个 View —— 安全，单次更新实测通常 20~50ms。

#### 三态渲染（按你的要求）

| 状态 | 渲染 |
|---|---|
| 今天 | 日期挂红色圆形背景（对应参考图的"19"红圈） |
| 有任务 · 未完成 | 任务文字 `#BDBDBD` 浅灰 |
| 有任务 · 已完成 | 任务文字主色 + 加粗，**永久保留显示** |
| 无任务 | 文字留空 |

**关键行为：已完成的任务不会从卡片上消失。** 它和未完成的任务占同一个位置，只是换了颜色 —— 就像纸上写过的字，做完了不等于撕掉。

（下文举例中的 A、B 指**同一条规则下的两个任务**，共享规则的重复与提醒、各自独立打卡。）

**并且一次打卡会让整周的所有命中日同步变色**：周一把 A 打了卡，周一到周五五格里的 A 同时从灰变高亮，但文字全都还在。这不是"删掉重画"，是五个格子查到了同一条打卡记录。

因为卡片上"已完成"和"未完成"共享同一个视觉位置，**颜色区分必须是第一眼可辨的**，建议：
- 未完成：`#BDBDBD`（浅灰，低存在感）
- 已完成：主色（如 `#FF6B35`）+ 加粗，或加一个 8dp 的对勾角标

而不是"已完成变浅"（很多 todo 应用的划掉做法）—— 那会让人以为没做。

**一个格子里有多条任务时**（如周一同时有 A 和 B），按 §6.2.1 的三档密度规则决定渲染几条。

#### 四条必须遵守的约束

1. **任务 Text 必须单行 + 省略号**（`maxLines = 1`）。换行会把整行高度撑变，下面几周位置全乱 —— 这是 RemoteViews/Glance 里最典型的布局崩坏。
2. **系统字体放大是必踩的坑**。用户把系统字体调到最大，13sp 会变成约 20sp，直接撑爆。对策：字号用 `sp` 但**格高用固定 `dp`**，并对格子内容做 `maxLines` 截断；或者在卡片里统一乘一个由 `Configuration.fontScale` 算出的反向缩放系数。
3. **格子里能放几条由尺寸档位决定**，溢出显示 `+N`。一格里同时有 A 和 B 是常态，`+N` 不是可选项而是必需。
4. **格子内选取优先级**：未完成优先，已完成排在后面。具体放几条见下面的三档规则。

#### 6.2.1 尺寸适配：三档响应式，按可用尺寸决定内容密度

算一笔账：每格「日期 13sp + 任务 9sp + 内边距」≈ 26dp，6 行 = **156dp**；加标题行 + 星期头 ≈ **40dp**；合计 **≈ 200dp**。所以 **4×5 的卡片（约 180dp 高）装不下任务名** —— 必须分档。

**统一规则：窗口/卡片越小，越只保留「未完成」；越大，越显示「多条 + 已完成」。**

| 档位 | 触发尺寸 | 格子内容 | 每格任务数 | 已完成怎么体现 |
|---|---|---|---|---|
| **紧凑** | 高 < 240dp（4×5） | 只显示**未完成任务**名 | 1 条 + `+N` | 底部一排 3dp 圆点：实心=已完成、空心=未完成 |
| **标准** | 高 240~340dp（5×5） | 未完成优先，剩余位置显示已完成 | 最多 2 条 | 已完成用主色加粗正常显示 |
| **宽松** | 高 > 340dp（6×6 / 平板） | 全部显示，字号可放大 1sp | 最多 3 条 + `+N` | 同上 |

**紧凑档用圆点弥补信息损失。** 4×5 下文字位置只够放一条未完成任务，但一天里可能有 A 和 B 两条 —— 圆点就是补偿：**点数 = 当天任务条数，实心 = 已完成、空心 = 未完成**。3 个点一眼就能读出"这天 3 条任务、2 条做完了"，既不占文字空间，也不丢失"完成痕迹永远在"的语义。

> 如果连圆点都不想要（极简），可以只显示未完成数的小角标。但完全不给完成痕迹会让用户失去"今天做了多少"的感知，建议保留圆点。

Glance 实现：

```kotlin
SizeMode.Responsive(
    setOf(
        DpSize(250.dp, 180.dp),   // 紧凑
        DpSize(320.dp, 300.dp),   // 标准
        DpSize(400.dp, 400.dp),   // 宽松
    )
)

// provideGlance 里读 LocalSize.current，按高度选渲染分支
```

`appwidget-provider.xml` 声明：

```xml

android:targetCellWidth="5" android:targetCellHeight="5"   <!-- Android 12+ 默认放 5×5 -->

```

**默认落 5×5（标准档）**，用户缩小到 4×5 自动切紧凑，放大到 6×6 自动切宽松。

#### 刷新时机

| 时机 | 手段 |
|---|---|
| 应用内数据变更 | `MyWidget().updateAll(context)` 立刻刷新 |
| 跨天（"今天"要换格子） | `updatePeriodMillis="1800000"`（30 分钟，系统允许的最小值）+ `onUpdate` 里用 `AlarmManager.set(RTC, 次日 00:00)` 兜一次 |
| 增删卡片 / 尺寸变化 | Glance 自动处理 |
| 开机 | `BOOT_COMPLETED` 里重刷 |

跨天用**非精确的 `AlarmManager.set()`**（差几分钟无所谓），可以避开 Android 12+ 的精确闹钟权限，是个便宜的省事做法。

- **启动器网格密度**：设成 6×6 网格时实际 dp 尺寸会变

- **系统字体放大**（最可能出问题）
- **折叠屏展开/折叠**

### 6.3 提醒系统（闹钟 + 通知）

需求已确认为**精确到分钟**，并且规则级可选：通知 / 闹钟 / 两者 / 都不要 —— 落到字段上就是 `notify_on` 与 `alarm_on` 两个独立开关，规则下的任务继承。这块是 Android 端第二重的活，仅次于卡片。

#### 6.3.1 数据模型

提醒配置独立一张表，一条规则可以有 0~N 个提醒（例如"提前 30 分钟轻提醒 + 到点强闹钟"），规则下的任务**继承**所属规则的提醒：

```sql
CREATE TABLE reminder (
  id           TEXT PRIMARY KEY,
  owner_kind   INTEGER NOT NULL,          -- 0=规则（任务继承规则提醒） 1=记事 2=倒数日
  owner_id     TEXT NOT NULL,
  notify_on    INTEGER NOT NULL DEFAULT 0,-- 是否发通知
  alarm_on     INTEGER NOT NULL DEFAULT 0,-- 是否响闹钟
  time_of_day  TEXT NOT NULL,             -- 'HH:mm'，精确到分钟
  notify_text  TEXT,                      -- 通知文案，空则用「该打卡了：<任务名>」
  offset_days  INTEGER NOT NULL DEFAULT 0,-- 提前 N 天；任务类通常 0，倒数日用它
  repeat_rule  INTEGER NOT NULL DEFAULT 0,-- 0=只在周期第一个命中日 1=每个命中日
  snooze_min   INTEGER NOT NULL DEFAULT 0,-- 重复响铃间隔，0=不贪睡
  enabled      INTEGER NOT NULL DEFAULT 1,
  -- 同步三件套
  rev          INTEGER NOT NULL DEFAULT 0,
  updated_at   INTEGER NOT NULL,
  deleted      INTEGER NOT NULL DEFAULT 0,
  dirty        INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_reminder_owner ON reminder(owner_kind, owner_id);
```

两个开关的语义（用户能直接感知的行为，UI 上要写清楚）：

| 开关 | 取值 | 行为 |
|---|---|---|
| `notify_on` / `alarm_on` 提醒方式 | 通知 / 闹钟 | **通知 / 闹钟是两个独立开关，可单开、可双开；两者都关等价于「不提醒」。UI 上不允许出现「通知和闹钟都关但还显示在提醒中」的状态。** |
| `repeat_rule` 是否重复 | 不重复 | **只在该周期的第一个命中日响一次**（周一~周五的任务，周一响一次就够） |
| | 重复 | **周期内每个命中日都响**（周一到周五各响一次） |

> `repeat_rule` 正好对应上一轮提的"一个周期响几次"，做成**规则级开关**，规则下的任务继承，两种都支持。

#### 6.3.2 闹钟与通知的实现差异

| | 通知（Notification） | 闹钟（Alarm） |
|---|---|---|
| 调度 | `AlarmManager.setExactAndAllowWhileIdle()` | **`AlarmManager.setAlarmClock()`** |
| 表现 | 状态栏通知，可划掉 | 全屏 Intent + 响铃 + 震动，必须手动停 |
| 权限 | `POST_NOTIFICATIONS`（13+） | 精确闹钟权限 + `USE_FULL_SCREEN_INTENT` |
| 优先级 | 普通 | 系统里最高，Doze 下也精确 |

`setAlarmClock()` 是 Android 最强的定时 API：手机深度休眠也精确触发，还会在状态栏显示闹钟图标。代价是必须有精确闹钟权限。

#### 6.3.3 权限清单（这块是真正的卡点）

| 权限 | 何时需要 | 状态 |
|---|---|---|
| `POST_NOTIFICATIONS` | Android 13+ 发通知 | 运行时请求，用户可拒 |
| `SCHEDULE_EXACT_ALARM` | Android 12+ 精确闹钟 | **Android 14 起默认关闭**，必须在应用内检测并跳转引导用户开启 |
| `USE_EXACT_ALARM` | 想无条件使用 `setAlarmClock` | **Google Play 只批给闹钟/日历类应用**，需提交用途说明 |
| `USE_FULL_SCREEN_INTENT` | Android 14+ 全屏闹钟弹出 | 同上，14 起收紧 |
| `RECEIVE_BOOT_COMPLETED` | 重启后恢复闹钟 | 普通权限，但必须在 `BOOT_COMPLETED` 里重建 |
| `VIBRATE` / `WAKE_LOCK` | 闹钟震动与唤醒屏幕 | 普通权限 |

**三条必须处理的现实：**

1. **Android 14 起 `SCHEDULE_EXACT_ALARM` 默认是关的。** 启动时用 `AlarmManager.canScheduleExactAlarms()` 检测，为 `false` 时跳 `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` 引导。用户拒绝就**降级为不精确闹钟**（可能延迟几分钟到几十分钟），并在 UI 上如实告知，不能假装正常。
2. **纯自用/侧载可以不申请 `USE_EXACT_ALARM`** —— 用 `SCHEDULE_EXACT_ALARM` + 用户授权就够。要走 Google Play 且有真闹钟功能，才需要那个更严的权限。
3. **国产 ROM 才是真正的敌人。** 小米/华为/OPPO/vivo 会额外冻结后台、拦自启动、把通知静音。代码层面无解，只能做引导页：
   - 按 `Build.MANUFACTURER` 跳对应机型的自启动管理页
   - 引导加入「电池优化白名单」
   - **小米必须额外开「锁屏显示」和「后台弹窗」**，否则全屏闹钟根本出不来

#### 6.3.4 调度与恢复

```
提醒落表 reminder_schedule(reminder_id, task_id, occur_date, fire_at, snooze_until)   ← 实际注册的闹钟
  ├─ 开启：未来 90 天内的所有触发点滚动写入，逐个 setExactAndAllowWhileIdle / setAlarmClock
  ├─ 触发：BroadcastReceiver → 查库 → 发通知 或 起全屏闹钟 → 写 fired 记录
  ├─ 跨天：重新滚动补足未来 90 天
  └─ 重启：BOOT_COMPLETED → 清空已过期的 → 全量重建
```

要点：

- **`PendingIntent` 的 `requestCode` 必须唯一且稳定**（建议 `(reminderId.hashCode() shl 8) or dayIndex`），否则两个提醒会互相覆盖 —— 这是 AlarmManager 最常见的 bug。
- **重启后闹钟全部丢失**，`BOOT_COMPLETED` 必须重建，这是 Android 硬规则。
- **权限被撤销后已注册的闹钟会失效**，要在 `onResume` 里复查 `canScheduleExactAlarms()`。
- **兜底：打开应用时补算。** 算出"应该响但没响"的提醒并在应用内提示。漏一次提醒不至于丢数据，但要让用户知道系统没兑现。

#### 6.3.5 闹钟响铃与贪睡（Snooze）

闹钟响起来之后的行为要单独设计，这是「闹钟」区别于「通知」的全部意义。

**全屏闹钟界面**（`AlarmActivity`）：

```
┌─────────────────────────────┐
│                             │
│         09:00               │  ← 大字号时间
│         健身                │  ← 任务标题
│                             │
│                             │
│   ┌───────────┐ ┌─────────┐ │
│   │  贪睡 5 分钟 │ │  停止   │ │  ← 两个按钮，贪睡在左（次要）
│   └───────────┘ └─────────┘ │
└─────────────────────────────┘
```

**响铃实现：**

| 项 | 做法 |
|---|---|
| 唤醒屏幕 | `setShowWhenLocked(true)` + `setTurnScreenOn(true)`（API 27+），锁屏上直接显示 |
| 解锁 | `KeyguardManager.requestDismissKeyguard()` |
| 铃声 | `MediaPlayer` + `AudioAttributes.USAGE_ALARM`（走闹钟音量通道，不受媒体音量影响）；或用 `Ringtone` 更省事 |
| 音频焦点 | `AudioFocusRequest`，抢占音乐播放 |
| 震动 | `VibrationEffect.createWaveform(longArrayOf(0,1000,1000), 0)` 循环 |
| 前台服务 | `FOREGROUND_SERVICE_SPECIAL_USE`（Android 14+ 需要声明类型），保证响铃期间不被杀 |
| 超时自动停 | **响 5 分钟无操作就自动停止**，降级为一条常驻通知。不能无限响，否则手机变砖 |

**贪睡逻辑：**

```
点「贪睡 5 分钟」
  → 停止铃声与震动
  → 记录 snooze_count + 1
  → AlarmManager.setExactAndAllowWhileIdle(now + snooze_min*60_000, 同一个 PendingIntent)
  → 到点再次拉起 AlarmActivity
```

三个必须定的细节：

1. **贪睡时长**：`snooze_min` 字段已预留，默认 5 分钟，允许用户改成 5/10/15/30。
2. **贪睡次数**：不限次（和系统闹钟一致），但要记 `snooze_count` 写进日志 —— 用户回头能看见自己推了几次，这本身是个有用的数据。
3. **递增贪睡**（可选）：第 1 次 5 分钟、第 2 次 10 分钟、第 3 次 15 分钟封顶。这是系统闹钟的标准行为，对"真的起不来"的人更有用。**建议做成开关，默认关闭**（简单直接，用户想开再开）。

**多个闹钟同时触发**：如果 A 和 B 的提醒撞在同一分钟，用单例队列串行处理，第二个排在第一个停止或贪睡之后再拉起，不要同时叠两个 Activity（会闪屏甚至崩溃）。

#### 6.3.6 工作量

`setAlarmClock` + 全屏 Activity + 响铃 + 震动 + 贪睡 + 权限引导 + 重启恢复 + ROM 保活，**P4 从原来的 1~1.5 周上调到 2.5 周**。其中真机适配（小米/华为各一台）至少要占 3~4 天。

### 6.4 数据供给卡片

Android 侧是原生，卡片可以直接读 Room（同一个进程、同一个数据库文件），**不需要像 Tauri 方案那样绕 SharedPreferences 快照**。这是改用原生后省掉的一整块复杂度。

但建议仍然做一层轻量缓存：卡片渲染时不做复杂规则展开，而是读预计算表，由数据变更时和跨天时重算写入。好处是卡片刷新时延从几十毫秒降到几毫秒，且 App 被杀后卡片仍能正常渲染。

```sql
-- 月历卡片缓存：当月 42 天，每天要显示的任务条目
CREATE TABLE widget_month_cache (
  month     TEXT NOT NULL,     -- '2026-10'
  day       INTEGER NOT NULL,
  seq       INTEGER NOT NULL,  -- 当天第几条
  text      TEXT NOT NULL,
  done      INTEGER NOT NULL,
  PRIMARY KEY (month, day, seq)
);

-- 倒数日卡片缓存
CREATE TABLE widget_countdown_cache (
  memo_id   TEXT PRIMARY KEY,
  title     TEXT NOT NULL,
  days      INTEGER NOT NULL,  -- 正数=还有N天，负数=已过N天
  target    TEXT NOT NULL
);
```

### 6.5 倒数日卡片

倒数日需要**独立的第二个 widget**（和月历卡片是两个 AppWidgetProvider），布局极简：

```
┌────────────────────┐
│ 纪念日             │  ← 标题，左上角，12sp，次要色
│                    │
│        365         │  ← 天数，36sp，主色，居中
│         天          │  ← 单位，10sp
└────────────────────┘
```

Glance 实现约 25 行：

```kotlin
Column(GlanceModifier.fillMaxSize().padding(12.dp)) {
    Text(title, style = TextStyle(fontSize = 12.sp, color = 次要色))
    Spacer(GlanceModifier.defaultWeight())
    Column(
        modifier = GlanceModifier.fillMaxWidth(),
        horizontalAlignment = Alignment.CenterHorizontally,
    ) {
        Text("$days", style = TextStyle(fontSize = 36.sp, fontWeight = FontWeight.Bold, color = 主色))
        Text("天", style = TextStyle(fontSize = 10.sp))
    }
    Spacer(GlanceModifier.defaultWeight())
}
```

**方向处理**（对应你的例子）：

| 目标日期 | 显示 |
|---|---|
| 未来（2027-03-15） | `还有 152 天` |
| 今天 | `就是今天` |
| 过去（2025-10-19） | `已经 365 天` |

天数用 `ChronoUnit.DAYS.between(target, LocalDate.now())` 算取绝对值，正负号决定前缀是"还有"还是"已经"。

**倒数日的提醒**：`offset_days` 字段就是为它准备的 —— "还剩 N 天时提醒"。可以配多个提醒点（例如提前 30 天、7 天、1 天、当天各一次），每个点独立选通知/闹钟和具体时刻。这正好复用 §6.3 的 `reminder` 表，不需要第二套机制。

**多个倒数日怎么办**：卡片绑定其中一个（App 里长按倒数日 → "固定到桌面"），其余在 App 内看。不建议在卡片里做左右翻页 —— Glance 的 `AdapterViewFlipper` 支持不稳定，小卡片上翻页手势也容易误触。若日后需要，大尺寸（4×2）可以改成 2~3 条的迷你列表。

**跨天刷新**：和月历卡片共用同一套逻辑（30 分钟 `updatePeriodMillis` + `AlarmManager` 兜零点）。

**尺寸**：默认 2×2，声明 `minWidth="110dp" minHeight="110dp"`，放大到 4×2 / 4×4 时天数文字跟着变大即可。

### 6.6 笔记与记事的文档式编辑页

笔记（`kind=2`）与记事（`kind=0`）都不再用通用表单，改走**同一个全屏文档式页面**：一套布局、一套保存逻辑，两端的差异只落在顶栏与元信息行。

```
┌──────────────────────────────────┐
│ ‹      [分类 chip]           ⋯   │  ← 顶栏 52px
├──────────────────────────────────┤
│ 标题                             │  ← 1.625em，min-height 42px
│ 创建于 2026-10-20 · 128 字        │  ← 元信息行
│                                  │
│ 正文 textarea                    │  ← 无边框，行高 1.85，flex:1
│                                  │
└──────────────────────────────────┘
```

- **顶栏 52px**：左侧 `‹` 返回，中间按类型切换（见下表），右侧 `⋯` 菜单
- **标题**：大号输入，`font-size: 1.625em`、`min-height: 42px`，无边框、占满整行
- **元信息行**：笔记显示创建日，记事显示日期区间或「未排期」；两者都附**实时字数**（正文一改就跟着变）
- **正文**：无边框 `textarea`，行高 `1.85`，`flex: 1` 吃满剩余高度。**不要给正文固定 `min-height`** —— 小屏会顶出屏幕、大屏会留一片空白，交给 flex 分配

顶栏按类型分叉，其余部分完全共用：

| 类型 | 顶栏中间 | 元信息行 |
|---|---|---|
| 笔记（`kind=2`） | 分类 chip：可切换分类、可新建分类 | `创建于 2026-10-20 · 128 字` |
| 记事（`kind=0`） | 隐藏 chip，改为日期区间的两个 `date` 输入 | `10/20 ~ 10/29 · 128 字` 或 `未排期 · 128 字` |

- **`⋯` 菜单只有两项**：复制正文 / 删除笔记。删除走**底部二次确认**，不做撤销 Toast；确认框的层级必须高于编辑页全屏层，否则被盖住点不到
- **自动保存**：600ms 静默防抖，标题或正文改完即落库，没有「保存」按钮
- **空壳不落库**：标题与正文**都为空**时不写 `memo` 行，退出即丢弃 —— 避免点一下「＋」就多出一条空记录
- **「≡ 创建思维笔记」为禁用占位**：始终 `disabled`、点击无响应，不做假功能（§10）

### 6.7 首页笔记本区

首页在**今日概览条下方**展示笔记本条目，让最近写的几条不用进配置页就能看见：

- 每条一行：分类 chip + 标题 + 正文单行省略
- **最多 3 条**；超过 3 条时右侧出「全部 ›」，跳配置页的笔记本分区
- 点任一行直接进 §6.6 的文档式编辑页
- **无笔记时整块隐藏**，不留空标题占位
- 渲染挂在今日概览条的重绘逻辑末尾，随它一起更新，避免首页各区块刷新不同步

## 7. 后端服务（Go）

### 7.1 接口

**只暴露一个业务接口，一次请求完成双向交换：**

```
POST /api/v1/sync
Authorization: Bearer <token>

请求 {
  "deviceId": "uuid",
  "sinceRev": 12345,
  "rules":       [ ...本地 dirty 的 rule... ],
  "tasks":       [ ...本地 dirty 的 task... ],
  "memos":       [ ...本地 dirty 的 memo... ],
  "completions": [ ...本地 dirty 的 completion... ]
}

响应 {
  "serverRev": 12400,
  "rules":       [ ...rev > sinceRev 的记录... ],
  "tasks":       [ ...rev > sinceRev 的记录... ],
  "memos":       [ ...rev > sinceRev 的记录... ],
  "completions": [ ...rev > sinceRev 的记录... ],
  "conflicts":   [ { "id": "...", "reason": "rule_modified_both_sides" } ]
}
```

不拆成 push + pull 两趟 —— 中间失败会产生"推上去了但没拉回来"的半同步状态，很难排查。

> **实现状态（2026-10-24）：首期实际拆成了 `POST /api/sync/push` 与 `GET /api/sync/pull?since=` 两个接口。**
>
> 偏离理由：pull 需要分页（首次同步可能上万条），而 push 不需要；两者的失败原因不同（网络 vs 仲裁逻辑），分开重试更容易定位。
>
> 原设计的顾虑（半同步）实际风险可控，因为 **push 是幂等的**：LWW 仲裁按 `updated_at`，同一条记录重复推结果相同。客户端只要把 `lastPulledRev` **仅在 pull 成功后推进**，push 成功而 pull 失败时，下次会带着新的 `maxRev` 重推一遍，不会产生数据错乱。
>
> 未做：`Authorization: Bearer <token>` 鉴权、`/api/v1/export` 全量导出、`/api/v1/rev` 查版本号、`conflicts` 上报（§7.2 第 4 条）。这些留到多设备场景落地时补，见 §11。

辅助接口：

- `GET /api/v1/health` — 前端配置页"测试连接"用
- `GET /api/v1/export` — 全量导出（备份，也是"后端挂了数据还在"的保险）
- `GET /api/v1/rev` — 只查版本号

### 7.2 合并规则（只在这一个地方实现）

1. 服务端为每条记录维护全局单调递增的 `rev`（`rev = ++globalRev`）。
2. 客户端推上来的记录，若 `sinceRev` 之后服务端又改过同一条 → 冲突，按 LWW 裁决：`updated_at` 大者胜；**完全相等时按 `deviceId` 字典序 tie-break**（保证多端算出相同结果，这一步不能省）。
3. **打卡与提醒记录同样走 LWW by `updated_at`**：同一 `(task_id, period_start)` 由 `updated_at` 大者胜，相等时比 `rev`，再相等保留服务端值。

   > **本节原方案（"取 `status` 最大值"）已废弃。** 打卡是**可撤销**的：取最大值会让「取消打卡」永远同步不过去，另一端始终显示已完成。
   >
   > 实测证据（2026-10-24，Go 同步接口）：push 一条 `status=0, updated_at=5000` 的取消记录后，`/api/month` 对应周期立即从 `done:true` 回到 `false`。若按 `max(status)` 实现则会停在 `true`。
   >
   > 提醒排程同理按 `updated_at` 仲裁。完整协议见 `docs/本地优先契约.md` §7.2。
4. **规则字段冲突要上报**：`repeat_mode` / `weekdays_mask` / `month_day` / `year_month` / `year_day` / `start_date` / `end_date` 这些字段两端都改过时，LWW 会静默丢掉一边。这种情况放进 `conflicts` 返回，前端提示"该规则在两端被同时修改"，让用户裁决。**数据静默丢失比多一次点击糟糕得多。**

### 7.3 离线与失败

- 同步是后台异步任务，**失败绝不阻塞 UI、绝不覆盖本地数据**
- `dirty` 标记保证推失败的数据下次接着推
- 状态呈现：`未配置 / 同步中 / 已同步（3 分钟前）/ 失败：无法连接`
- **首次接入时做差异预览**：万一误配到一个有旧数据的后端，让用户先看到会覆盖什么

### 7.4 局域网部署（默认形态）

**定位：整个软件默认在局域网内运行，不依赖公网。** 客户端本地 SQLite 独立可用；后端只是局域网内的一台常开设备，负责多端合并。

#### 7.4.1 后端跑在哪

| 载体 | 适不适合 | 说明 |
|---|---|---|
| **NAS（群晖/绿联/威联通）** | ✅ **最优** | 24 小时开机、有固定内网 IP、有 Docker，天然适合 |
| 树莓派 / 软路由 | ✅ 好 | 同上，功耗更低 |
| 家里常开的台式机 | ⚠️ 可以 | 关机后同步暂停（但**不影响本地使用**，这是本地优先架构的价值） |
| 云服务器 | ❌ 本方案不需要 | 既然确定局域网，就不做公网部署 |

提供一个 Docker 镜像 + 一个各平台单文件二进制，用户随手丢哪都能跑。

#### 7.4.2 服务发现：客户端怎么找到后端

三层降级，任意一层通了就行：

```
① mDNS（首选，零配置）
   Go 后端注册服务：_took._tcp.local  →  带 version / port / deviceName
   Android 用 NsdManager 发现
   PC 用 Rust 的 mdns-sd crate 发现
   → 用户什么都不用填，装好就能连

② UDP 广播（mDNS 被拦时兜底）
   客户端向子网广播地址发 TOOK_DISCOVER
   后端回应 TOOK_ANNOUNCE { ip, port, version }
   → 需要先算本机网段（Android: LinkProperties；PC: os.networkInterfaces）

③ 手动填 IP:端口（永远可用，也是排查手段）
   配一个「测试连接」按钮打 /health
```

**mDNS 的现实问题**（必须知道）：部分企业 WiFi、访客网络、开了"AP 隔离"的路由器会拦多播；Windows 防火墙默认也可能拦 5353/UDP。所以 ①②③ 必须都实现，不能只做 mDNS。

发现流程对用户来说应该是一句话：「正在查找局域网内的 Took 服务…」→ 找到就显示设备名 → 点连接。

#### 7.4.3 安全（局域网不等于安全）

局域网内最大的威胁是**同一个 WiFi 下的其他人**（公司、宿舍、咖啡厅）。所以认证不能省：

| 措施 | 说明 |
|---|---|
| **Bearer Token** | 后端首次启动生成并打印到控制台，客户端配置时输入一次。**必做** |
| **只绑定局域网地址** | 不要监听 `0.0.0.0`，绑定本机内网 IP（可配置）。避免路由器做了端口映射时意外暴露到公网 |
| `/health` 免认证 | 只返回服务名和版本号，供发现探测用，不带任何业务数据 |
| Payload 加密（可选但建议） | 用 Token 派生 AES-256-GCM 密钥加密请求体。局域网内成本很低，记事本内容值得这一层 |
| 不做 HTTPS | 自签证书的信任链配置成本高于收益，对称加密够用。**若日后要公网访问，再上 Caddy 自动证书** |

**要在设置页明确写一句**：不要在路由器上给这个端口做端口映射 —— 这是局域网方案唯一容易把数据送出去的口子。

#### 7.4.4 局域网方案的固有限制（接受它）

- **手机连着移动数据时同步不了**，回到家连上 WiFi 才会同步。本地功能全程不受影响。
- 如果确实需要在外同步，标准解法是 **WireGuard / Tailscale 之类的内网穿透**，让手机"看起来在家里的局域网"。这属于用户的自选配置，不做进产品，文档里提一句即可。
- 后端所在设备关机 → 同步暂停，但两端照常可用，下次开机自动补上。

### 7.5 关键约定

- 不做多用户、不做账号体系 —— 单用户自托管，这是刻意简化
- Token 只放 Header，不要放 URL（会进访问日志）
- 后端启动时把「服务地址 + Token」打印在控制台，方便用户在客户端填一次

## 10. 明确不做的事

- **锁屏卡片**：AOSP 没有通用 API，只有厂商私有扩展，覆盖机型少、维护成本高
- **点对点同步 / 配对码**：设备之间不直连、不需要两两配对，统一走局域网内那一个后端。（UDP 广播只在"发现后端"时用一次，不承载数据，§7.4.2）
- **标准 RRULE 兼容**：自研受限规则集更可控
- **多用户 / 账号体系**：单用户自托管
- **iOS**：明确列在目标之外
- **倒数日卡片翻页**：多个倒数日靠"固定到桌面"选一个，不做卡片内翻页（Glance 的 AdapterViewFlipper 不稳、小卡片手势易误触）
- **思维笔记（用户可编辑的思维导图）**：本期不做，界面上以禁用按钮占位，不提供任何假功能（§6.6）

## 11. 已确认 / 剩余待确认

**已确认（实现依据）：**

- ✅ 一个任务是**整体的一件事**，不按天拆分（规则下可以有多个任务，每个任务各自独立打卡；它们共享规则的重复与提醒）；打卡按**周期**一次，周期内所有命中日共享状态（§3.1）
- ✅ 打卡后**整周所有命中日同步变成已完成**，但文字全部保留、不消失
- ✅ 不强制在某天完成，周期内任意命中日打卡等效
- ✅ 没勾选的日子不出现（B 勾周一 + 周五，周二三四无 B）
- ✅ Android 卡片 / PC 窗口按尺寸自适应：**小只显示未完成，大显示多条**（§5.5、§6.2.1）
- ✅ PC 的"固定桌面"= **WorkerW 贴壁纸层**（`Win+D` 后可见）
- ✅ Android 走**原生 Kotlin**，PC 走 Tauri，**共用一个后端**
- ✅ 提醒精确到分钟，通知与闹钟是**两个独立开关**，可单开也可同时开；「不提醒」是互斥重置项，`repeat_rule` 可选是否每个命中日都提醒（§6.3）
- ✅ **闹钟带贪睡**，默认 5 分钟、可不限次、可选递增（§6.3.5）
- ✅ 倒数日：目标日期 + 天数（未来=还有 N 天，过去=已经 N 天），支持提前 N 天提醒（可配多个点），独立卡片默认 **2×2**（§3.8、§6.5）
- ✅ PC 端提醒与 Android 对等（通知 + 置顶闹钟窗口 + 贪睡）
- ✅ 重复方式五种：每周固定几天 / 每 N 天（1~3660，带预设）/ 每月某日（含月末钳制与「每月最后一天」）/ 每年某月某日 / 不重复（§3.2、§3.3）
- ✅ 管理页按类型分区：规则 / 记事 / 倒数日 / 笔记本；**类型由所在分区决定**，表单里不再有类型切换器
- ✅ 记事日期可留空（不排期），也可填结束日期形成时间段，区间内每一天都显示
- ✅ 笔记本：非时间性记录，只有名称与正文，带分类，不进日历与打卡
- ✅ 笔记与记事共用一套文档式全屏编辑页，字段差异只在顶栏（分类 chip vs 日期区间）与元信息（§6.6）
- ✅ Android 首页在今日概览条下方展示笔记本条目（最多 3 条，超过出「全部 ›」）（§6.7）
- ✅ 笔记正文为空时黄色「创建思维笔记」按钮保持禁用，不做假功能
- ✅ 统计分析：时间范围 × 统计类型两个维度，数据全部由本地状态实时计算，不写死（§3.7）
- ✅ PC 窗口支持整体透明度（40%~100%）、吸附屏幕边缘、收起为贴边小三角
