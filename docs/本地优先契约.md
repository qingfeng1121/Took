# 本地优先 · 跨端共享契约

> PC、Android、后端三端各有本地库；同步是后续里程碑。本文件是**三端必须逐字一致的行为契约**，
> 任何一端改了语义，另外两端必须同改，并更新本文件的用例表。

## 1. 为什么本地优先

- 没网也能看日历、能打卡（这是打卡类应用的底线体验）。
- 后端退化为「同步中介」，不参与每次渲染；断网时它不在关键路径上。
- 代价：**重复规则引擎要写三遍**（Go / Rust / Kotlin），所以第 3 节的用例表就是三端的共同验收标准。

## 2. 数据模型（四表，字段与 docs/schema/*.json 一致）

| 表 | 主键 | 关键字段 |
|---|---|---|
| `rule` | id | repeat_mode / weekdays_mask / repeat_every / month_day / year_month / year_day / start_date / end_date / repeat_until |
| `task` | id | rule_id（外键）、title、enabled、sort_order |
| `completion` | (task_id, period_start) | status：0 未完成 / 1 已完成 |
| `memo` | id | kind：0 记事 / 1 倒数日 / 2 笔记本；start_date / end_date / category |

每条记录都带同步四件套：`rev`、`updated_at`（毫秒）、`deleted`（软删，永不物理删除）、`dirty`（本地未推送）。

## 3. 重复规则引擎（三端实现必须一致）

### 3.1 枚举

```
repeat_mode: 0=weekly 1=every 2=monthly 3=yearly 4=none
weekdays_mask: bit0=周一 … bit6=周日（注意 Go 的 Weekday 是 周日=0，需要换算 (weekday+6)%7）
month_day: 1..31，-1 表示「每月最后一天」
```

### 3.2 命中判定 `occursOn(rule, date) -> bool`

1. `date < start_date` → **false**（起始日之前一律不命中）
2. 上界 = `repeat_until`（空则用 `end_date`，两者都空则不限）；`date > 上界` → false
3. 按 repeat_mode 分派：
   - **weekly**：`(weekday+6)%7` 对应的 bit 置位才算命中
   - **every**：`daysBetween(start, date) % repeat_every == 0`（repeat_every 必须 ≥1，否则 false）
   - **monthly**：`date.day == min(month_day, 该月天数)`；`month_day == -1` 取该月最后一天。
     **钳制只决定这一次落哪天，不改写用户填的值**（填 31，2 月落 28，3 月仍回 31）
   - **yearly**：`date.month == year_month` 且 `date.day == min(year_day, 该月天数)`。
     2/29 在平年落 2/28，**且不溢出到 3/1**
   - **none**：`date == start_date`

### 3.3 周期归属 `periodStartOf(rule, date) -> 'YYYY-MM-DD'`

打卡键 = `taskId + ":" + periodStart`，**同一周期内所有命中日共享一个完成状态**。

| repeat_mode | periodStart |
|---|---|
| weekly | 该周周一 |
| every | `start + floor(daysBetween(start,date)/N)*N` |
| monthly / yearly / none | 就是 date 本身（一周期一天） |

### 3.4 日期约定

- 一律用 `'YYYY-MM-DD'` 字符串。**禁止**用 epoch 毫秒算日期（跨时区/夏令时会整片漂移一格）。

非法日期按**分层**处理，两层都要做到，不能只做一层：

| 层 | 要求 | 理由 |
|---|---|---|
| **写入**（新增/编辑/导入/同步落库） | 严格校验，非法格式`2026-1-5`、`2026/10/01`、`2026-02-30` **必须拒绝并报错** | 脏数据一旦落库，会在每次渲染时反复出错 |
| **读取/展开**（`occursOn` 等纯函数） | 解析失败返回 `false`，**不抛异常** | 月历渲染不能因为一行脏数据整体崩溃 |

三端现状：Go 的 `OccursOn` 在读取层返回 false（符合本表第二层），但尚未实现写入层校验——写路径落地时必须补 `ValidateDate`。
Kotlin 的 `DateKeys.parse` 抛 `IllegalArgumentException`，属于写入层语义，读取层调用处需自行兜底。

## 7. 同步协议（首期：局域网推拉 + 时间戳仲裁）

后端不参与渲染，只做**同步中介**。客户端永远先写本地（同时置 `dirty=1`），再找机会推。

### 7.1 两个接口

```
POST /api/sync/push
  请求: { rules:[], tasks:[], memos:[], completions:[] }   // 只传 dirty=1 的记录
  响应: { accepted: {rules:n, tasks:n, memos:n, completions:n}, maxRev: 整数 }
  
GET  /api/sync/pull?since=<rev>
  响应: { rules:[], tasks:[], memos:[], completions:[], maxRev: 整数, hasMore: bool }
  // 返回 rev > since 的所有记录（含 deleted=1 的墓碑）
```

`push` 服务端对每条记录：按 id 找到已有行 → 冲突仲裁（见 7.2）→ 写入 → `rev = 服务端当前 maxRev + 1`，`dirty` 由客户端清零（服务端不回传 dirty）。

**布尔语义字段在同步 JSON 里一律用 `0/1` 整数，不用 `true/false`。** 涉及 `enabled`、`notify_on`、`alarm_on`、`deleted`、`dirty`、`status`。

> 理由：三端的本地库都是 SQLite，这些列本来就是 INTEGER 0/1；如果 JSON 用 bool，客户端要多做一层转换，而转换点分散在三个语言里最容易漂移。2026-10-24 就出过一次：Go 的 `SyncRule.Enabled` 是 `bool`，PC 发 `0/1`，push 直接 400「cannot unmarshal number into bool」，整条同步链断裂。统一成 0/1 后，「库里是什么、线上是什么」完全一致。

### 7.2 冲突仲裁

| 表 | 规则 |
|---|---|
| rule / task / memo | **LWW by `updated_at`**：时间戳大者赢；相等时比 `rev`，大者赢；再相等则保留服务端原值（幂等） |
| completion | **同样 LWW by `updated_at`**，不用 `max(status)` |

> completion 为什么不用「取 status 最大值」：打卡是**可撤销**的。取 max(status) 会让「取消打卡」永远同步不过去，另一端始终显示已完成。用 updated_at 仲裁才能表达「最后操作者赢」，与用户预期一致。
> 这一条与定稿 §7.2 原文（「取 status 最大值」）冲突，**以本节为准**，定稿需同步修订。

### 7.3 删除

永远软删：`deleted=1` + 新的 `updated_at` + `dirty=1`。墓碑随 pull 下发，对端据此本地软删。**不得物理 DELETE**，否则会被另一端同步回来「复活」。

### 7.4 客户端状态

本地存两个游标：
- `lastPulledRev`：上次成功 pull 到的 rev，下次 `since` 传它；
- `dirty` 标记：任何本地写操作都置 1，push 成功后由客户端清零。

失败处理：push 或 pull 失败**不回滚本地数据**，只保留 dirty，下次重试。离线优先的含义就是「网络失败不是错误，只是稍后再试」。

### 7.5 首期不做

- 不做实时推送（WebSocket），只在启动、手动触发、以及每 5 分钟尝试一次；
- 不做多设备仲裁的向量时钟，单用户单账号场景 LWW 足够；
- 不做端到端加密（局域网自部署，见定稿 §7.4.3 的说明）。

## 5. 首期范围（只读月历）

1. 本地库建表 + 种子数据
2. 按月展开：每天命中的任务 + 打卡状态
3. 网格渲染：42 格、三档密度（<720 compact / 720~1080 standard / >1080 loose）
4. 点日期数字开面板；**格子里任务名是纯预览，点了不响应**
5. 打卡状态按 (task_id, period_start) 着色
6. **不做编辑**：不提供新增/修改/删除入口

## 9. 编辑语义（写路径）

所有写操作统一：`updated_at = 当前毫秒`、`dirty = 1`、`rev` 保持不变（由服务端推拉时分配）。**删除一律软删**（`deleted=1`），绝不物理 DELETE。

### 9.1 新增规则

- 必填：`title`、`start_date`；至少一个任务；`repeat_mode=0` 时 `weekdays_mask` 不能为 0；`repeat_mode=1` 时 `repeat_every` 在 1..3660
- `id` 客户端生成，全局唯一

### 9.2 修改规则 —— 分两类，**这条最重要**

| 改动内容 | 处理方式 | 理由 |
|---|---|---|
| `title` / `enabled` / 提醒设置 | **原地改** | 不影响哪天命中，历史记录天然保留 |
| `repeat_mode` / `weekdays_mask` / `repeat_every` / `month_day` / `year_month` / `year_day` / `start_date` | **裂开（split）**：旧规则 `repeat_until = 昨天`（原地改，原地 `updated_at` 刷新），另生成一条新规则承载新设置，任务与打卡记录留在旧规则下不动 | 直接改会重算历史命中日，等于洗掉上个月的打卡记录——这是打卡类应用最典型的翻车方式 |

裂开的细节：
- 「昨天」= 今天 − 1 天，格式 `YYYY-MM-DD`
- 旧规则的 `end_date` 若为空且 `repeat_until` 为空，才写入 `repeat_until`；已有更早的上界则不覆盖
- 新规则的 `start_date` = 今天
- **裂开后默认勾选「复制任务到新规则」**，并在勾选项旁显示「将复制 N 个任务」。复制生成**新 id** 的新任务，旧规则下的任务与打卡一条不动 —— 复制不是搬家，历史归属不变。用户可以取消勾选。

> **为什么默认勾选**：默认不勾时，用户只是改了个重复设置，新规则下却没有任何任务，观感上等于「任务全没了」，很容易误判成数据丢失。而复制产生新 id、不触碰旧记录，风险为零，所以默认勾选更符合预期。
- 裂开后旧规则在列表里显示为「已结束」，仍可查看历史，不可再编辑重复设置
- **提醒的处理**：裂开时把提醒**复制到新规则**（同样的双开关与时刻/文案/贪睡），旧规则保留它自己那条提醒不动。理由：提醒是「以后怎么提醒」的配置、不是历史事实，用户改周几之后仍想在原时间被提醒；而旧规则已封口、不会再产生命中日，它那条提醒是惰性的、不会触发，保留它让「当时怎么配的」有据可查。

### 9.3 删除规则

- 规则及其下**所有任务**一并软删（`deleted=1, updated_at=now, dirty=1`）
- 该规则的**提醒也要一并软删**：提醒挂在规则上，规则没了提醒就没有意义；不级联会产生指向已删规则的孤儿行，既浪费同步流量，将来若做「恢复规则」还会把旧提醒意外带回来
- 打卡记录（completion）**不删**：它们是历史事实，且删了会在另一端「复活」
- 删除前 UI 必须二次确认并写明影响条数：「将删除该规则及其 N 个任务（打卡历史保留）」

### 9.4 任务增删改

- 新增：继承当前 `rule_id`，`sort_order` 取当前最大值 +1
- 改名 / 启停：原地改
- 删除：软删任务；**它名下的打卡记录同样不删**

### 9.5 同步与编辑的关系

编辑产生的记录全部带 `dirty=1`，由既有的 push 流程推上去。裂开一次会产生两条记录（旧规则改 + 新规则增），两条都要带上。

### 9.6 三端共同验收用例（编辑）

| # | 场景 | 断言 |
|---|---|---|
| E1 | 只改 title | 规则 id 不变，`repeat_until` 不变，历史打卡仍在 |
| E2 | 把 weekdays_mask 从 31 改成 42（周一到周四+周六） | 旧规则 `repeat_until` = 昨天；新增一条规则 `start_date` = 今天；旧规则下任务与打卡一条不少 |
| E3 | 删除规则（含 2 个任务） | 规则 deleted=1、两个任务 deleted=1、completion 行数不变 |
| E4 | 给规则加一个任务 | 新任务 `rule_id` 正确、`sort_order` 递增、dirty=1 |
| E5 | 删除任务 | 任务 deleted=1，其 completion 行数不变 |
| E6 | 编辑后不带 dirty 的记录不存在 | 所有被改过的行 dirty 都应为 1 |

## 10. 记事 / 倒数日 / 笔记本的编辑语义

这三类同住 `memo` 表（`kind` 0/1/2），**不挂规则、不进打卡统计**，所以没有「裂开」概念——任何字段都可原地改。

### 10.1 各自的字段约束

| kind | 类型 | 必填 | 可空 | 说明 |
|---|---|---|---|---|
| 0 | 记事 | `title` | `start_date` / `end_date` | 两处都空 = 不排期；只有 start = 单日；start+end = 时间段，**区间内每天都显示** |
| 1 | 倒数日 | `title`、`start_date`（目标日） | `content`（备注） | 目标日可以是过去（显示「已经 N 天」）或未来（「还有 N 天」） |
| 2 | 笔记本 | `title` | `content` / `category` | 分类默认「未分类」，由用户自建；不进日历 |

### 10.2 写入规则

- 全部 `updated_at = 当前毫秒`、`dirty = 1`、`rev` 保持
- 删除一律软删（`deleted=1`）
- 记事改日期区间 → 原地改（日历上命中日随之变化，这是它的本意，不存在历史保护问题）
- 笔记本改分类 → 原地改；分类名本身由 `category` 字段承载，**不单独建分类表**（首期）
- 删除笔记本/记事时，UI 需二次确认；不涉及打卡记录，无需提示「历史保留」

### 10.3 三端共同验收用例（memo）

| # | 场景 | 断言 |
|---|---|---|
| M1 | 新建记事（不排期，start/end 都空） | 落库成功；月历上任何一天都不出现；列表能看到 |
| M2 | 把记事改成时间段 10/27~10/29 | 月历上三天都出现该记事；10/26 与 10/30 不出现 |
| M3 | 新建倒数日（目标日 2027-03-15） | 落库成功；不进月历；列表显示目标日 |
| M4 | 新建笔记本（分类「习惯」） | 落库成功；不进月历；分类正确 |
| M5 | 删除记事 | `deleted=1`，`updated_at` 变大，`dirty=1`；列表不再显示它 |
| M6 | 三类的新建/编辑/删除后 | 所有被改过的行 `dirty` 都为 1（待同步） |

### 10.4 与原型的一致性

原型 `prototype/pc.html` 与 `prototype/android.html` 里这三类的编辑形态**已验收**，实现时直接照抄：
- 记事与笔记本在两端都用「文档式全屏页」：大号标题 + 元信息 + 无边框正文
  - 记事元信息：`10/27 ~ 10/29` 或 `10/20` 或 `未排期`
  - 笔记本元信息：`更新于 10月24日 下午6:24 ｜ N 字`
    > 不是「创建日」：`memo` 表只有 `updated_at`，没有 `created_at`。**不加这一列**——加了会破坏三端 schema 同构，而「更新于」对笔记类内容反而更有用（能看出最后改动时间）。这是对原型措辞的有意修正。
- 记事顶栏显示日期区间两个输入，笔记本顶栏显示分类 chip
- 倒数日沿用普通表单（标题 + 目标日 + 备注）

## 11. 提醒（通知 + 闹钟）

提醒挂在**规则**（`owner_kind=0`）或记事/倒数日（`1`/`2`）上，落 `reminder` 表，schema 见 `docs/schema/reminder.schema.json`。规则下的任务**继承所属规则的提醒**，不单独配。

### 11.1 两个独立开关，而不是三选一

| 状态 | 含义 |
|---|---|
| `notify_on=1, alarm_on=0` | 只发通知（状态栏 + 提示音，不打断） |
| `notify_on=0, alarm_on=1` | 只响闹钟（全屏 + 响铃 + 震动，必须手动关） |
| `notify_on=1, alarm_on=1` | 两者都要 |
| **两个都是 0** | **非法**：schema 用 `anyOf` 拦死。想不提醒就软删这行，或 `enabled=0` |

UI 上体现为「不提醒 / 通知 / 闹钟」三个按钮，但语义是：**「不提醒」是互斥重置项**（点了把两个开关都清零并退出），「通知」「闹钟」各自独立切换。五种点击序列都不允许出现「三项全灭」的中间态。

**墓碑豁免**：`deleted=1` 的行不受「至少开一个」约束。墓碑是删除标记、不是提醒状态，客户端删除时常先把开关清零再打删除标记；若墓碑也校验，删除就永远同步不到对端。存活行（`deleted=0`）严格校验，`enabled=0` 不豁免。

### 11.2 其余字段

| 字段 | 含义 |
|---|---|
| `time_of_day` | `HH:mm`，精确到分钟。**通知与闹钟共用这一个时刻**，不设 notify_time / alarm_time 两个字段 |
| `notify_text` | 通知文案，空则用「该打卡了：<规则名>」 |
| `repeat_rule` | 0=只在周期第一个命中日提醒；1=每个命中日都提醒 |
| `snooze_min` | 贪睡间隔分钟，0=不贪睡 |
| `offset_days` | 提前/延后 N 天；倒数日常用负数（提前 N 天） |

### 11.3 首期范围（重要）

**只做「存与显示」，不做真实调度。**

- 本轮：三端能存提醒、能在表单里配、能同步、规则列表能显示「通知 21:00 + 闹钟 09:00」这样的摘要
- 不做：`AlarmManager` 注册、PC 通知栏、贪睡的实际响铃——这些是平台能力，需要真机与系统权限，见定稿 §6.3.3 的权限清单
- 这样切分的原因：提醒的**数据模型**和**调度实现**是两件事，前者三端一致、可测；后者平台差异极大（Android 的精确闹钟权限、PC 的置顶窗口），混在一起做会导致「一端通一端不通」难以判断进度

### 11.4 三端共同验收用例（提醒）

| # | 场景 | 断言 |
|---|---|---|
| R1 | 规则配「通知 21:00」 | 落库 `notify_on=1, alarm_on=0`；列表摘要「通知 21:00」；`dirty=1` |
| R2 | 再打开闹钟 | `notify_on=1, alarm_on=1`；摘要「通知 21:00 + 闹钟 21:00」（**两者共用同一个 `time_of_day`**） |
| R3 | 点「不提醒」 | 该提醒行软删或 `enabled=0`；列表摘要不显示提醒 |
| R4 | 试图保存两个开关都关的提醒 | 写入层**拒绝**（schema `anyOf` 已拦） |
| R5 | 提醒随规则一起同步 | push 后后端 `reminder` 表有该行；另一台 pull 得到 |

### 7.6 跨语言端到端验证结论（2026-10-25 实测）

之前所有「同步通过」都是各端跟自己的 mock 对话（PC 的进程内 mock、Android 的裸 ServerSocket、Go 的自己发自己收），**没有一条跨语言**。本轮用真实报文做了验证：

**方法**：不手写报文，而是让 PC 端用**它自己的 `schema.sql` 建库 + 自己的写路径插入 + serde 序列化**生成 payload（模拟器在 `server/_e2e/pcshape`）；Android 形状按其 `RuleStore.kt` / `ReminderStore.kt` / `MemoStore.kt` 的 `put()` 语句逐键还原。两份报文打进同一个 Go 服务端。

**结论**：

| 检查项 | 结果 |
|---|---|
| `enabled` / `notify_on` / `alarm_on` / `deleted` 类型 | ✅ 两端都发 number，Go 回 number |
| `completion` 主键 `(task_id, period_start)` | ✅ 两端一致 |
| `updated_at` 单位 | ✅ 都是毫秒 |
| PC 与 Android 数据共存同一后端 | ✅ 3 规则 / 2 任务 / 3 memo / 2 提醒 / 2 打卡 |
| 往返幂等性 | ✅ pull 结果原样回推，`accepted` 全 0、`maxRev` 不变（零写放大） |

**唯一天然的形状差异（无害，但要知道）**：

| 字段 | PC 推 | Go 存 | Go 回 | 语义 |
|---|---|---|---|---|
| `end_date` / `repeat_until` | `null` | 归一为 `""` | `""` | 都是「不限」；PC 的 `empty_to_null` 会把 `""` 再转回 NULL，闭合 |
| `repeat_every` 等模式无关字段 | `null`（weekly 时） | 归一为 `0` | `0` | PC 的 `needs_split` 对 weekly 只比 `weekdays_mask`+`start_date`，不进比较，无害 |

> 这三处之所以无害，靠的是**两端的归一化逻辑正好互补**：Go 把 `null` 收成空值，PC 把空值再转回 NULL。如果哪天有人去掉其中一边的归一化，就会变成真漂移。所以这条要作为已知约束保留在文档里，而不是「反正现在没问题」。

### 11.5 原生闹钟的两个必需声明（实测踩坑，2026-10-25）

要把闹钟交给系统时钟（`AlarmClock.ACTION_SET_ALARM`），Android 端**必须**同时满足两条，缺一条就静默退回应用自绘响铃：

| # | 声明 | 缺失时的症状 |
|---|---|---|
| 1 | `<uses-permission android:name="com.android.alarm.permission.SET_ALARM" />` | `startActivity` 被 AMS 拒绝：`Permission Denial: ... requires com.android.alarm.permission.SET_ALARM` |
| 2 | `<queries><intent><action android:name="android.intent.action.SET_ALARM" /></intent></queries>` | Android 11+ 包可见性：`resolveActivity()` 返回 `null` |

**这两条的坑在于症状会互相伪装**：缺 `<queries>` 时 `resolveActivity` 返回 null，看起来像「系统没有时钟 App」；缺权限时 `resolveActivity` **能成功**、`clockAppAvailable()` 显示 true，看着一切正常，直到 `startActivity` 才抛 `SecurityException`。所以只查「能不能解析」不足以下结论，**必须实际启动一次并看日志**。

真机验证（小米 13 / 5bf0cda4 / Android 15，系统时钟 `com.android.deskclock`）：加这两条之前 `system_alarm` 表恒为空、系统时钟里没有 `[Took]` 闹钟；加上之后日志出现 `已交给系统时钟：label=[Took] 单词打卡 23:55`，系统时钟 App 的闹钟列表里出现 `[Took] 单词打卡`。

## 12. 并发开发约定（多代理协作）

同一台真机（`adb`）、同一个 Gradle 工程、同一个 Tauri 工程，**都不允许两个代理同时操作**。

### 12.1 真机设备锁

`.device-lock.md` 是唯一的锁记录。用真机前先读「当前持有者」：

| 状态 | 动作 |
|---|---|
| `空` | 写入自己（任务名 + 开始时间）再开始 |
| 非空且不是自己 | **不要抢**，先做不占设备的工作，稍后再查 |
| 是自己 | 继续，测完改回 `空` 并追加历史 |

### 12.2 排序原则

- **阻塞优先**：某任务不做则后续全部无法进行（如 widget 的 receiver 缺失导致整包不编译），它先拿锁。
- **可绕行则绕行**：若自己有个任务阻塞、但有别的能独立做且不占设备（纯函数单测、UI 布局），先做那个，把占设备的排后面。
- **禁止互相等待**：A 等 B、B 等 A 死锁时，由调度指定唯一持锁者，另一方立即转做不占设备的工作。

### 12.3 同目录并行的硬约束

两个代理同时改同一个工程时，必须**按目录划清边界**，且约定：

- 各自只碰自己的文件；对方目录即使编译不过也不许改、不许删、不许注释掉
- 无法单独跑通整工程编译时，验收标准改为「`compileDebugKotlin` 的报错清单里没有我的文件」
- 单测用 `--tests '包.*'` 隔离跑；跑不了就说明原因，不许跳过

> 教训（2026-10-25）：两个代理同时改 `android/`，A 的 `widget/` 半成品导致 B 的整包编译失败（4 个 unresolved reference），B 被卡住。B 的做法是对的——它没有为了让编译通过而删改 A 的代码，而是列出自己改过哪些文件自证清白，并主动上报冲突。

### 11.6 两端提醒的平台差异（必须知道，不是缺陷）

同一份提醒数据，两端「响」的方式不同。这是平台能力差异，不是实现不完整：

| 维度 | Android | PC |
|---|---|---|
| 精确性 | `setAlarmClock` 系统级，休眠也准 | 进程内线程 30 秒轮询，**最坏晚 30 秒** |
| 休眠/挂起 | 系统唤醒 | **不保证**（进程被挂起就跳过） |
| 声音通道 | `USAGE_ALARM` 独立，不受媒体音量影响 | `PlaySoundW` 走系统默认输出，**受媒体音量影响** |
| 震动 | 有 | 无此能力 |
| 原生闹钟 | `ACTION_SET_ALARM` 交系统时钟 | 无对应机制，只能置顶自绘窗 |
| 贪睡 | 系统时钟/应用内 | 应用内内存队列，不改数据库 |

> PC 端之所以不用 `setAlarmClock` 那种系统级机制，是因为 Windows 没有等价的「应用可预约的精确唤醒 + 系统闹钟列表」API；`Task Scheduler` 可做精确唤醒但需要管理员权限写任务，对「本地优先、免安装」的定位不合适。这个取舍是明确的，不是遗漏。

> 还有一个实现上的关键差异：**PC 的调度线程活在进程里**，所以必须拦住关窗（`prevent_close` + 隐藏 + 托盘），否则用户点了 X 进程就结束，提醒全部消失。Android 不存在这个问题（闹钟在系统里）。实测证据：`pc/shots/reminder-fired-window-closed.json` 显示 `visible_windows_after_close=0`、`fired_after_window_closed=true`、进程 PID 不变。

### 11.7 桌面组件的系统差异（Android 平台）

应用内「把组件放到桌面」走 `requestPinGlanceAppWidget`，这是 Android 8+ 的标准 API。**但国产 ROM 的支持度不同**：

| 系统 | `requestPinAppWidget` 行为 | 备注 |
|---|---|---|
| 原生 Android（AOSP） | 弹系统确认框，用户点「添加」即上桌面 | 标准路径 |
| MIUI / HyperOS（实测 小米 13 / Android 15） | **返回 `ok=true` 但不弹确认页**，界面会停在「正在把月历添加到桌面…」 | 需用户手动：长按桌面 → 小部件 → 找到 Took → 拖到桌面 |

**这意味着不能只靠 API**：应用内入口必须**同时**给出「手动添加」的文字指引，并且在系统不弹框时如实告知，不能假装成功。当前实现已如此（`ok=false` 时显示「这个桌面不支持自动添加，请长按桌面 → 小部件 → 找到「月历」」）。

> 已知一个反直觉现象：同一台 MIUI 上「今日概览」组件能出现在桌面，而「月历」组件的 pin 请求不弹框——两者 provider 定义、receiver 结构、SizeMode 实现几乎相同。原因是今日概览是通过**桌面长按 → 小部件 → 手动拖**放上去的，不是走 pin API。所以这不是代码差异，是添加路径不同。

### 12.4 PC 贴壁纸层的三种 PinMode 与已知限制

`PinMode` 是运行时探测出来的，不是写死的：

| 模式 | 触发条件 | 行为 |
|---|---|---|
| `WorkerW` | 找到承载 `SHELLDLL_DefView` 的 WorkerW 兄弟窗口 | `SetParent(hwnd, WorkerW)` + `WS_CHILD` |
| `ProgmanTopChild` | **Win11 24H2**：DefView 直接挂 Progman，没有可用 WorkerW | `SetParent(hwnd, Progman)` + `WS_CHILD` + 显式 `HWND_TOP` 抢 z-order |
| `FallbackAlwaysOnTop` | 连 Progman 都拿不到 | 普通置顶窗口，界面上如实告知 |
| `Disabled` | 用户关闭 / Explorer 重启后放弃 | 还原 `SetParent(NULL)` + 摘 `WS_CHILD` |

**本机实测（Win11 24H2 / explorer 10.0.26100.8875 / RDP）落 `ProgmanTopChild`**：顶层 12 个 WorkerW 全部 `vis=False`、`rect 0,0,202,56`、零个承载 DefView，`Progman` 上 `progman_has_def_view=true`。

**已知限制（如实记录，不是遗漏）**：

1. **Explorer 重启会连带销毁挂在 Progman 下的窗口**（`lastErr=1400`），Tauri 的窗口注册表清不掉旧 label，重建必报 `already exists`。当前降级为「置 Disabled + 提示重启应用」。真要修得换架构（顶层窗口轮询维持 z-order，或窗口销毁时整进程重启），代价超出本模块范围。
2. **多显示器**只挂主屏 Progman，未按显示器匹配各自宿主。
3. **Wallpaper Engine 类动态壁纸**会抢 WorkerW，未做冲突提示。
4. **RDP 下 `BitBlt` 不可用**，截图只能用 `PrintWindow(Progman, PW_RENDERFULLCONTENT)` 渲染子树，不是屏幕抓取；该条在验收里单列为 SKIP。

**取小部件尺寸而非全屏铺满是有意选择**：全屏铺满技术上可行，但会让用户点不到桌面图标；保持小部件尺寸则图标区不被遮挡（实测 `hit_icon_zone_is_self=false`），且窗口本身仍可交互。此选择写在代码注释与设置页面板里。

### 7.7 conflicts 的判定与 winner（2026-10-26 定稿）

**判定条件与胜负无关**：同一 id，且 `updated_at` 与 `rev` **都不相等**，且 7 个规则字段之一确有差异。

> 这一点最初实现错了，值得留档：只在「客户端赢」时比对字段，服务端赢时直接短路返回。后果是「两端都改过、但客户端时间戳更早」时，客户端这次的改动被丢且 `conflicts` 为空——正是 §7.2 第 4 条要防的静默丢失。LWW 语义本身没错（最终状态一致），错的是「只上报一半的丢失」。

**`winner` 字段是必需的，不是可选**：

| 取值 | 用户语义 | 前端该怎么处理 |
|---|---|---|
| `client` | 我这次的改动**覆盖**了另一端 | 通常静默重拉即可 |
| `server` | 我这次的改动**被丢了** | **必须明确提示**「你的改动被另一端覆盖」 |

两个方向的用户影响正相反。没有这个字段，前端只能猜方向，猜错就正好落回要防的静默丢失。

响应示例（`winner=server`，`accepted` 全 0、`maxRev` 不涨）：

```json
{ "accepted": {"rules":0,"tasks":0,"memos":0,"reminders":0,"completions":0}, "maxRev": 2,
  "conflicts": [{ "id":"r_sw", "table":"rule", "reason":"rule_fields_both_modified",
                  "winner":"server", "clientUpdatedAt":1000, "serverUpdatedAt":2000,
                  "fields":["repeat_mode","month_day"] }] }
```

无冲突时返回 `[]`（不是 `null`），客户端可直接遍历。
